## 2. 各芯片职责边界（面试核心论据）

### 2.1 ESP32-P4 = HMI / AI
**只做**：显示渲染、触摸交互、图像采集与推理、协议主机侧、网络应用层、存储管理、OTA 主机。
**不做**：硬实时控制、直接驱动继电器/水泵/锁。

理由：
- P4 上跑 LVGL 渲染 + AI 推理，任务抖动不可控。让这类系统去控制一台水泵，是典型的实时性设计错误。
- **故障域隔离**：P4 在 OTA 升级、崩溃重启、UI 卡顿时，家里的执行器必须保持安全状态。这是把执行控制下放到独立 MCU 的根本原因，不是为了"用满两块板"。

### 2.2 ESP32-C6 = 无线协处理器
**只做**：把射频能力提供给 P4。
关键认知：**ESP32-P4 没有任何射频**（这是 P4 的设计定位——它是一颗纯"主机"芯片）。C6 通过 SDIO 与 P4 相连，运行 `esp_hosted` 的 slave 固件，P4 侧用 `esp_wifi_remote` 组件后，**应用层代码与在普通 ESP32 上写 Wi-Fi 几乎完全一样**（`esp_wifi_init()` / `esp_wifi_connect()` 照常调用）。

这带来两个必须理解的点：
1. **C6 固件与 P4 应用固件是两套独立固件**，分别烧录、分别升级（C6 的 slave 固件通常一次性烧录，除非需要升级 hosted 版本）。
2. **SDIO 是共享资源**：若同时使用 microSD（SDMMC），需要确认总线是否冲突（P4 有多个 SDMMC 控制器，通常不冲突，但要在阶段 0 确认清楚）。

> 💼 **这是简历上很少见的技能点。** 大多数人只会说"我用了 ESP32 的 Wi-Fi"，你能说"我理解主机-协处理器架构，通过 SDIO 跑 esp_hosted，主机侧用 esp_wifi_remote 使射频对应用层透明"。

### 2.3 STM32F103C8T6 = 实时控制节点
**只做**：传感器采集、执行器控制、本地安全保护、掉电数据保存、协议从机侧。
**不做**：图形界面、网络协议栈、复杂算法。

理由：F103C8T6（72MHz Cortex-M3、64KB Flash、20KB RAM）资源有限但**足够且可控**，它的价值是：
- **确定性**：裸机或轻量 RTOS，任务周期可预测
- **5V 容忍 IO**：许多传感器/继电器模块是 5V 逻辑，与 P4 的 3.3V 直连有风险
- **独立兜底**：即使 P4 完全死机，F103 仍能执行"气体超标就报警"这类安全逻辑

> ⚠️ **注意 20KB RAM 是很紧的**。协议缓冲区、日志环形缓冲、OLED 显存（1024 字节）都要精打细算。**这个约束本身是好事**——面试时"我在 20KB RAM 的 MCU 上如何设计缓冲策略"是一个非常有料的话题。

### 2.4 ESP32-C3 = 低功耗无线节点
把 P4 的 C6 当作"主控的射频"之后，远场节点用独立 MCU 是更合理的设计：
- 节点需要**电池供电 + 深度睡眠**，这跟常开的中控是两个完全不同的功耗域
- ESP-NOW 让它与 P4 直连，**不经过路由器**，延迟更低、断网仍可用
- 它复用阶段 2 定义的帧格式 → 证明协议设计的可复用性

## 3. 软件分层

### 3.1 P4 侧（ESP-IDF + FreeRTOS）

```
┌─────────────────────────────────────────────────────┐
│ 应用层   场景引擎 │ 设备抽象层 │ 告警管理 │ 设置管理    │
├─────────────────────────────────────────────────────┤
│ UI 层    LVGL 页面(首页/房间/设备/告警/设置) + 主题字体  │
├─────────────────────────────────────────────────────┤
│ 服务层   设备管理器(影子状态) │ 视觉服务 │ 网络服务      │
│          (维护设备模型 + 离线标记)  (esp-dl)  (MQTT)   │
├─────────────────────────────────────────────────────┤
│ 通信层   协议主机(v2) │ MQTT client │ ESP-NOW(节点)     │
├─────────────────────────────────────────────────────┤
│ 驱动层   UART(DMA+IDLE) │ MIPI-DSI+触摸 │ MIPI-CSI │ SD │
│          esp_hosted(Wi-Fi) │ I2C │ GPIO │ ES8311 音频  │
├─────────────────────────────────────────────────────┤
│ 系统层   FreeRTOS 任务/队列/事件组 │ NVS │ 分区表 │ OTA │
│          任务看门狗 │ 堆监控 │ core dump             │
└─────────────────────────────────────────────────────┘
```

**FreeRTOS 任务划分（2026-10-18 按 `app_main.c` 与各模块实况复核）：**

| 任务 | 优先级 | 周期/触发 | 职责 | 注意 |
|---|---|---|---|---|
| LVGL 主任务 | — | `esp_lvgl_adapter` 内部 | LVGL 渲染与事件处理 | LVGL **不是线程安全的**，必须单任务持有，跨任务访问需锁 |
| `proto_poll` | 5 | 10ms 轮询 | 收包、TX 重传、链路状态机、HELLO 协商与 PING 保活 | 启动时独立创建，**不依赖主循环**（免被 LCD/Wi-Fi 初始化阻塞） |
| `weather` | — | 后台循环 | 等 Wi-Fi → SNTP 授时 → 拉取天气，只写状态快照 | 不触碰 LVGL；失败按指数退避 |
| `wallpaper` | — | 逐帧 | JWP 壁纸解码与帧投递（`frame_sink` + `lv_async_call`） | 待机层隐藏时 `wall_pause()` 让出带宽 |
| `vision_task` | — | PIR 事件 | 采集→推理→上报 | **事件驱动，不常开** |
| `wifi_reconn` | 5 | Wi-Fi 事件 | Wi-Fi 断线重连 | 重连不能阻塞其它任务 |

> 说明：主任务自身在 `app_main` 末尾的主循环里也调用 `AppProto_Poll()`/`rule_runtime_tick()`/喂狗，与独立 `proto_poll` 任务并存；规则引擎评估周期 200ms。

> ⚠️ **两个必须遵守的规则**：① LVGL 只能在一个任务里调用；② 中断服务程序里只做"投递队列"，绝不做耗时操作。违反了这两条，问题会以"偶发死机"的形式出现，极难排查。

### 3.2 F103 侧

```
┌─────────────────────────────────────────────────────┐
│ 应用层   本地安全逻辑(气体报警/水泵超时/链路失效安全态)      │
├─────────────────────────────────────────────────────┤
│ 协议层   协议从机(v2): 收包状态机 │ 组包 │ ACK/重传      │
├─────────────────────────────────────────────────────┤
│ 服务层   设备状态机(执行器) │ 标定表(R0/干湿两点) │ 日志  │
├─────────────────────────────────────────────────────┤
│ 驱动层   ADC │ GPIO │ EXTI │ TIM(PWM/微秒延时) │ I2C │ SPI│
├─────────────────────────────────────────────────────┤
│ 系统层   IWDG 看门狗 │ 复位原因诊断 │ AT24C06 掉电存储    │
│          W25Q64 环形日志 │ 可选 FreeRTOS 或裸机前后台      │
└─────────────────────────────────────────────────────┘
```

**架构选择建议**：阶段 1 先用**裸机 + 定时器节拍**（简单、可控、易调试），阶段 2 引入协议后如果时序管理变复杂，**再重构到 FreeRTOS**。
> 💼 这个"先裸机后 RTOS"的重构本身就是好故事：*"我为什么把它重构成 RTOS？因为裸机下的协议超时重传和传感器轮询互相干扰，出现了响应延迟毛刺，实测数据是 X。"*

## 4. 数据流示例（把架构跑一遍）

### 4.1 采集体温 → 显示在面板（正常路径）
```
DHT11 → F103 (TIM 微秒时序读取) → 标定/单位换算 → 存入影子状态
  → 协议从机组包(温度, 序号=N) → UART → P4
  → CRC 校验通过 → ACK 回 F103 → 投递到设备管理器队列
  → 设备管理器更新影子状态 → 通知 LVGL → lv_label_set_text
  → (若启用) MQTT 发布到 home/panel/sensor/temperature
```

### 4.2 面板点击开灯（控制路径）
```
触摸事件 → LVGL 回调 → 设备管理器 action(light, ON)
  → 记录"本地操作时间戳"（用于云指令仲裁）
  → 协议主机组包 → UART → F103 → CRC 校验 → ACK
  → F103 驱动继电器 → 回读 GPIO 状态 → 上报实际状态
  → 若 100ms 内未收到 ACK → 重传（最多 3 次）→ 仍失败则 UI 显示"控制失败"
```
> ⚠️ 注意最后一步：**UI 显示"控制失败"这个设计很重要**。绝大多数 hobby 项目在这里直接乐观更新 UI（点了就变绿），这是错的——真实产品必须区分"指令已发出"和"执行已确认"。

### 4.3 气体超标告警（安全路径，P4 死机也不能失效）
```
MQ-135 → F103 ADC → Rs/R0 → 超阈值(含迟滞)
  → F103 本地直接驱动蜂鸣器告警（不经过 P4！）
  → 同时上报 P4 → 面板弹窗 + MQTT 推送 HA
```
> 💼 **这是全项目最能体现"故障域隔离"价值的例子**：安全告警路径不依赖 P4。面试时讲这个，比讲任何 API 都有说服力。
> ✅ **2026-10-18 补记**：上报通道已补齐（ADR-009 落地）——F103 在 MQ-4/MQ-135 ≥60% 且 `quality==VALID` 时**上升沿立即上报 `ALARM_EVENT`**、之后每 30s 节流重发；P4 收下存入告警影子并回 `ALARM_EVENT_ACK`，在对应设备出现新鲜有效且低于阈值的读数时自动解除 active。本帧只用于"通知面板显示"，蜂鸣/关断仍在 F103 本地完成。面板卡片上屏列入「阶段四补完」。

### 4.4 人到家自动开灯（主动智能，事件驱动）
```
PIR 触发 → P4 中断 → 唤醒 vision_task
  → 摄像头采集 1~3 帧 → JPEG 硬件编码
  → esp-dl 人脸检测（INT8）→ 识别结果
  → 匹配到已登记人脸 → 触发场景"回家"
  → 开灯 + 面板显示访客信息 + 摄像头指示灯亮
  → 完成后摄像头断电休眠（不常开）
```

## 5. 关键设计决策索引

详细论证见 `docs/05-决策记录-ADR.md`：

| 编号 | 决策 | 一句话理由 |
|---|---|---|
| ADR-001 | 双 MCU（P4 + F103）分工，而非单芯片 | 实时性 + 故障域隔离 |
| ADR-002 | P4↔F103 用自定义二进制协议，而非 AT 指令/JSON | 带宽、确定性、错误检测能力 |
| ADR-003 | 首版用 UART，预留 RS485/CAN 升级 | 成本与复杂度权衡，留演进路径 |
| ADR-004 | 本地优先（Local-First），云为旁路 | 智能家居的核心体验是"断网还能用" |
| ADR-005 | 设备抽象层用"属性/动作/事件"模型 | 新增设备类型不改 UI 代码 |
| ADR-006 | 人脸数据端侧处理不上云 | 隐私合规 + 带宽 |
| ADR-007 | 摄像头事件触发而非常开 | 功耗 + 寿命 + 隐私 |
| ADR-008 | 使用 esp_hosted 让 C6 做射频，而非额外加一块 Wi-Fi 模块 | 板载资源、架构干净、学到主机-协处理器模型 |
| ADR-009 | F103 承载安全告警兜底逻辑 | 故障域隔离，P4 死机不失效 |
| ADR-010 | ~~钛丝锁强制限时通电由硬件定时器兜底~~ **已废弃** | 锁不接入：实装模块买错，`app_lock`/`bsp_lock` 已删（2026-10-18） |

> 完整决策集见 `docs/05-决策记录-ADR.md`（**ADR-001 ~ ADR-023，共 23 条**）；本表只列架构层主干。

## 6. 资源预算（阶段 0 后填实测值）

| 资源 | P4 | F103C8T6 | ESP32-C3 |
|---|---|---|---|
| CPU | 2× RISC-V @400MHz | Cortex-M3 @72MHz | RISC-V @160MHz |
| RAM | 768KB 内部 + 32MB PSRAM | **20KB**（很紧） | 400KB |
| Flash | 16MB | **64KB**（很紧） | 4MB |
| 预算占用 | UI 缓冲→PSRAM；图像缓冲→PSRAM；协议缓冲→内部 RAM | 协议缓冲 ~1KB；OLED 显存 1KB；日志环形缓冲留 512B~1KB | 采集+上报，睡眠为主 |
| 实测/待填 | | | |

> ⚠️ F103C8 的 **64KB Flash 要装下**：协议栈 + 全部传感器驱动 + OLED 字库 + IAP bootloader（IAP 需要双区，阶段 8 时要仔细规划分区，必要时裁剪字库或升级到 C8T6 的 128KB 兼容型号）。
>
> 📌 **F103 实测体积（2026-10-18 本机构建）：Debug 构建 FLASH 46044 B / 64KB（70.26%）、RAM 8584 B / 20KB（41.91%）—— 实测值，非估算。**
