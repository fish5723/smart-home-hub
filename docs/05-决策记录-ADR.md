# 架构决策记录（ADR）

> 用途：记录**每个重要决策的背景、备选方案、选择理由和代价**。
> 💼 **这是简历/面试的黄金素材**：面试官问"你为什么这么做"，你能说出备选方案和被放弃的原因，档次立刻不同。
> 格式：ADR-NNN，每条包含 背景 / 备选 / 决策 / 理由 / 代价 / 状态。

## ADR-001 · 采用双 MCU 分工（P4 管交互 + F103 管实时控制）

**背景**：手上有 ESP32-P4（强算力、强显示、带 MIPI）和 STM32F103C8T6（弱算力、强实时）。是否可以让 P4 直接控制继电器与传感器，去掉 F103？

**备选方案**
1. 单芯片：P4 全干（界面 + 传感器 + 执行器）
2. 双芯片：P4 管 HMI/AI，F103 管实时控制（**选定**）
3. 三芯片：再加一颗专用控制 MCU

**决策**：方案 2。

**理由**
- **实时性**：P4 上跑 LVGL 渲染与 AI 推理，任务抖动在毫秒到几十毫秒级，且不可预测；而执行器控制（尤其钛丝锁的脉冲断电、水泵的超时保护）需要确定性时序。
- **故障域隔离**：P4 会在 OTA 升级、崩溃、UI 卡死时重启。**主控重启不应该让家里的水泵失控。** F103 独立运行安全逻辑（气体告警、水泵超时）不依赖 P4。
- **电气原因**：F103 的 IO 与许多 5V 传感器/模块衔接更自然；P4 的 3.3V IO 直连 5V 负载有风险。
- **面试价值**：这套分工对应真实工业产品的"主控 + 从控"结构。

**代价**
- 必须定义并维护一套跨芯片通信协议（额外工作量，见 ADR-002）
- 两套固件、两套调试流程、两个升级路径（OTA + IAP）
- 状态一致性复杂度：会有"P4 状态"与"F103 实际状态"不一致的可能（用影子状态 + 回读解决）

**状态**：已接受

## ADR-002 · 自定义二进制协议（不用 AT 指令 / JSON）

**背景**：两个 MCU 之间怎么通信？

**备选方案**
| 方案 | 优点 | 缺点 |
|---|---|---|
| AT 指令（文本） | 简单、可直接打印调试 | 冗余大、解析脆弱、难表达结构化数据、无法高效传二进制 |
| JSON over UART | 可读性好、易扩展 | **带宽浪费 5~10 倍**、F103 上解析开销大（20KB RAM 吃紧）、无内建检错 |
| 自定义二进制 + CRC16（**选定**） | 紧凑、检错强、确定性好 | 需要自己写规范/状态机/解析工具，调试不直观（需配套 PC 工具） |

**决策**：自定义二进制协议（见 `docs/03-通信协议规范.md`）。

**理由**
- 115200bps 下每帧开销必须小：传感器每秒上报 8~10 个值，JSON 会让带宽迅速吃满。
- **需要真正的错误检测**：杜邦线 + 电机干扰环境下必须有 CRC，而不是简单校验和。
- 二进制协议强制你思考字节序、长度、版本、兼容性——**这本身就是嵌入式通信的核心能力**。
- 用自定义协议可以实践 ACK/重传/TTL/去重等**真实工业协议机制**，这是简历上的差异点。

**代价**
- 调试不直观 → **必须配套做 PC 端解析工具**（已列入阶段 2 交付物）
- 加字段需要维护版本兼容策略（用能力位图 + 未知类型忽略来化解）

**状态**：已接受

## ADR-003 · 首版物理层用 UART，预留 RS485 / CAN 升级

**背景**：P4 与 F103 之间的物理层选什么？

**备选方案**：UART(TTL) / RS485 / CAN(TWAI + bxCAN) / SPI / I2C

**决策**：**首版 UART TTL 115200**，协议帧格式与物理层解耦，保留升级到 RS485 或 CAN 的路径。

**理由**
- UART 零额外成本，两块板直接连线即可，调试最快（可接 USB-TTL 到 PC 抓包）。
- RS485 需要 MAX485 收发器（¥5），CAN 需要 SN65HVD230（¥5）——**都是很便宜的升级项**，但没有必要在第一版就引入。
- **关键在于协议分层**：帧格式、CRC、ACK 机制在物理层之上，换物理层不需要重写协议栈。**这是分层设计的实际收益。**
- 加 RS485/CAN 是后期很好的一个"技术纵深"加分项（抗干扰、长距离、多节点总线）。

**代价**：TTL UART 在长线/强干扰下不可靠（杜邦线超过 20~30cm 且靠近电机线时容易误码）。**这正好成为协议层容错机制的实测场景。**

**状态**：已接受

## ADR-004 · Local-First（本地优先）：云是旁路，不是主路

**背景**：控制指令走本地（P4 直接控制）还是走云（MQTT → HA → 回传）？

**决策**：**本地优先**。所有控制与联动在本地闭环完成；MQTT/HA 用于状态上报与远程访问，不参与本地控制的关键路径。

**理由**
- 智能家居的核心体验是"**按了就要立刻动，断网也要能开灯**"。走云往返会引入几百毫秒到数秒的延迟与不确定性。
- 断网、路由器重启、云服务故障都是常态，本地优先保证基础可用性。
- 这一条会带来一个具体的工程问题：**云指令与本地操作冲突时谁赢？** 决策为"**以操作时间戳为准，本地操作后 1 秒内的云指令不生效**"，并把规则写进测试用例。

**代价**
- 需要维护"本地状态"与"云状态"的收敛逻辑（重连后必须全量同步，不能假设状态没变）
- HA 侧看到的设备状态可能短暂滞后于真实状态

**状态**：已接受

## ADR-005 · 设备抽象层采用"属性 / 动作 / 事件"模型

**背景**：UI 如何与设备解耦，使得新增设备类型不用改 UI 代码？

**备选方案**
1. 每个设备写一个独立的 UI 页面与回调（最简单，但加设备就要改 UI）
2. 设备抽象层：统一设备模型 + 注册表 + 影子状态（**选定**）
3. 引入完整 MQTT/HA 的实体模型（过重）

**决策**：方案 2。设备模型定义：
```
Device {
  id, type, name,
  properties: [ {key, value, unit, quality, timestamp} ],   // 可读
  actions:    [ {key, params, handler} ],                    // 可写
  events:     [ {key, level, payload} ]                      // 可订阅
}
```
UI 只与设备管理器交互，不关心底层是 UART 还是 MQTT。

**理由**
- 这是 IoT 平台的通用做法（HA 的 entity/attribute、Matter 的 cluster/attribute 都是这个思路）。
- **可验证的收益**：新增"土壤湿度卡片"只需在配置表加一行，UI 代码零改动——这个演示会作为阶段 3 的验收标准。
- 同一个抽象层可以同时服务 UI、MQTT 上报、规则引擎三个消费者，避免三处各写一套状态管理。

**代价**：前期多写一层抽象（一会儿觉得"绕"），且必须严格约束自己**不把业务逻辑写进 UI 回调**，否则抽象会腐烂。

**状态**：已接受

## ADR-006 · 人脸数据端侧处理，默认不上云

**背景**：人脸识别结果/图像要不要传云端？

**决策**：**人脸检测与识别完全在 P4 端侧完成**，默认不上传人脸图像或特征到任何云端。上传的只有抽象的"有访客/是家庭成员"事件。

**理由**
- 人脸是敏感生物特征数据，上传即意味着数据可能被缓存、索引、泄露。
- 带宽与延迟：500 万像素图像上传要数秒，端侧推理只需百毫秒级。
- **产品合规意识**：摄像头工作时必须有可见指示灯（这是消费类产品的常见合规要求）。

**代价**：端侧算力受限，模型精度不如云端大模型；识别库容量受限于本地存储。

**状态**：已接受

## ADR-007 · 摄像头采用事件触发，不做常开

**背景**：视觉功能怎么触发？摄像头一直开还是按需开？

**决策**：**事件驱动**：PIR 检测到人 → 唤醒视觉任务 → 采集 1~3 帧 → 推理 → 上报 → 摄像头断电入眠。

**理由**
- **功耗**：常开摄像头（含 MIPI 链路与图像缓冲）会显著抬高整机功耗，而中控面板是全年插电设备，功耗就是电费与发热。
- **寿命与隐私**：摄像头与图像处理链路不是设计为 7×24 连续工作的；且常开意味着持续采集，隐私风险更高。
- **简历价值**："我对比过常开与事件触发两种模式的平均功耗"是一个很有力的证据。

**代价**：有触发延迟（PIR 响应 + 唤醒 + 采集，总计数百毫秒），不适合需要持续录像的场景；PIR 有误触发，需要防抖与"同一事件合并"逻辑。

**状态**：已接受

## ADR-008 · 用板载 C6 作为 P4 的射频（esp_hosted），不加额外 Wi-Fi 模块

**背景**：ESP32-P4 **没有射频**。联网怎么办？

**备选方案**
1. 额外接一块 ESP32/ESP8266 做 Wi-Fi 转串口（AT 固件）
2. 用板载 ESP32-C6，通过 SDIO 跑 `esp_hosted` + `esp_wifi_remote`（**选定**）
3. 用板载 RJ45 以太网

**决策**：方案 2 为主，以太网（方案 3）作为第二个网络接口做对照实验。

**理由**
- **这是板子本来的设计意图**：JC 模组把 P4 与 C6 封装在一起，就是为了解决 P4 无射频的问题。
- `esp_wifi_remote` 让应用层代码与"普通 ESP32 上写 Wi-Fi"几乎一致（`esp_wifi_init()` 等照常调用），**射频对应用层透明**——这是很优雅的分层。
- AT 固件方案（方案 1）会退化成"文本命令 + 简单解析"，可靠性、吞吐、延迟都更差。
- **学习价值极高**：主机-协处理器（host-coprocessor）架构在嵌入式里很常见（如 Linux 主控 + 无线模组），理解它等于拿到一个通用模型。

**代价**
- C6 固件与 P4 应用固件是**两套独立固件**，需分别管理（C6 的 hosted slave 固件通常一次性烧录）
- SDIO 总线可能与 microSD 共享资源，需在阶段 0 确认
- 调试链路更长：Wi-Fi 出问题时要先判断是 C6 侧还是 P4 侧

**状态**：已接受

## ADR-009 · 安全告警逻辑在 F103 本地兜底，不依赖 P4

**背景**：可燃气体超标是安全事件。告警是否由 P4 统一决策？

**决策**：**F103 本地直接判定并驱动蜂鸣器告警**，同时上报 P4 用于面板显示与云推送。P4 不参与"是否告警"的决策。

**理由**
- **故障域隔离**：P4 可能正在 OTA 升级、崩溃重启、UI 卡死。安全功能不能因此失效。
- 这也是"为什么要双 MCU"（ADR-001）最有说服力的实例——**架构决策要能举出具体场景，否则只是空谈**。

**代价**：告警阈值需要在 F103 本地也维护一份配置（配置同步逻辑增加）；两边阈值不一致会导致行为不一致（用统一的配置下发 + 校验解决）。

**状态**：已接受

> 📌 **2026-10-18 补记**：安全告警的**上报通道**（`ALARM_EVENT`）已补齐 —— F103 在 MQ-4/MQ-135 ≥60% 且 `quality==VALID` 时上升沿立即上报、之后每 30s 节流重发；P4 存入告警影子并回 `ALARM_EVENT_ACK`，数据恢复时自动解除。安全动作仍**全部在 F103 本地完成**（本地兜底结论不变）。见 `docs/16` 第六节。

## ADR-010 · 钛丝锁强制限时通电由硬件定时器兜底　⚠️ **已废弃（2026-10-18）**

**背景**：XG07E 是 SMA（形状记忆合金）钛丝锁，靠通电加热钛丝收缩实现动作。**持续通电会永久损坏钛丝。**

**决策**
- 驱动路径：`GPIO → MOSFET 模块 → 钛丝锁`（绝不 GPIO 直驱）
- 通电动作用**独立硬件定时器（如 TIM）控制断电**，不依赖主循环或软件流程
- 软件层再有第二重超时保护（双保险）
- 状态必须**回读**（有反馈信号则读反馈；无反馈则读驱动回路的电流/电压特征）

**理由**
- 钛丝锁的失效代价很高（拆机更换），而"软件流程被打断导致没断电"是很容易发生的事故。
- **硬件兜底 + 软件二次保护**是安全关键功能的通用模式（类似看门狗与硬件保护的关系）。

**代价**：占用一个定时器资源；逻辑稍复杂（要处理"定时器已启动时又来一条指令"的并发情况）。

**状态**：~~已接受~~ → **已废弃（2026-10-18）**：**锁不做**（实装门锁模块与设计不符，模块买错，决策 B4）；`app_lock`/`bsp_lock` 已删除，PB8 仍由 act_manager 独占写、默认锁定电平。本条仅作历史记录，见 `docs/16`。

## ADR-011 · 复用策略：只挑 A 档模块逐个搬运，不 fork 全量后删业务

**背景**：手上有两个前序工程——`smart-learning-box`（ESP32-P4，**同款 JC-ESP32P4-M3-DEV 板**，127 个源文件）与 `smart_home`（STM32F103，11 类外设驱动）。是否整块 fork 过来删掉不用的业务？

**备选方案**
1. `cp -r` 整个工程 → 删掉 NES 模拟器、教育 UI、云端搜题业务（**最快，但最脏**）
2. 新建干净工程，**只搬 A 档模块，搬运时当场修缺陷**（**选定**）
3. 完全不复用，从零重写（浪费 3~4 周已验证的 bring-up）

**决策**：方案 2。

**理由**
- **缺陷会被一起搬进来**。前序工程的三份审计报告（`AUDIT_REPORT.md` / `CRASH_AUDIT_REPORT.md` / `THREAD_AUDIT_REPORT.md`）显示**约四成问题未修**：字体加载 44 秒无看门狗、SD/WiFi 时钟冲突无守卫、Wi-Fi 扫描列表跨任务无锁、`HAL_MAX_DELAY` 无限阻塞、lcd/touch 初始化失败即 `abort()` 造成无限重启。如果 fork 全量，这些会静默地留在代码里，等到压力场景才爆，而那时你已经忘了它是继承来的。
- **删业务比搬模块慢**。NES 模拟器有 40+ 个 mapper 文件、`InfoNES.c`、`nes_ppu.c`… 要判断删干净需要通读，成本高于只搬 A 档。
- **顺手就把缺陷修了**。逐个模块搬运时，每个模块的缺陷就在眼前，修完立刻能用新工程验证。
- **资产分级本身就是可写进简历的能力**（见路线图阶段 10 的 v2 卖点）。

**代价**
- 搬运工作量比 `cp -r` 大（要逐个确认依赖）
- 需要读三份审计报告并逐条核对"修了没有"（这次已经做完，结论固化在 `docs/08-复用资产清单.md`）

**状态**：已接受

## ADR-012 · 精确锁定 `esp_hosted` **3.0.9**，禁止再用范围依赖

**背景**：P4 无射频，Wi-Fi 由板载 C6 经 SDIO 跑 `esp_hosted` 提供。组件版本怎么选？

**决策（2026-10-18 修订）**：实际使用 **`espressif/esp_hosted 3.0.9` + `espressif/esp_wifi_remote 1.6.5`**，并已在 `main/idf_component.yml` **精确锁定**（`==3.0.9` / `==1.6.5`），不再写范围依赖。

**理由**
- 新工程实测走通了 3.0.9 + 1.6.5 组合，必须**承认并锁定**它，而非回退到旧版（决策 B1）。
- **踩坑教训**：原先写范围（`>=2.11` / `>=1.6.5`）时，component manager 会拉到 **3.0.9**，而该版本**配置符号已更名**——保留旧符号会导致全新生成 `sdkconfig` 时配置错误。因此"锁定"必须是精确 `==`。
- **历史背景（保留）**：前序工程曾锁定 **2.9.6**，其组件清单注释写明"**经版本回归验证：2.12.9 会必现 SDIO 258 错误，2.9.6 无此问题**"——这是花时间踩出来的结论，作为背景保留而非现行锁定值。
- 同时把 `CONFIG_ESP_HOSTED_TRANSPORT_RESTART_ON_FAILURE` 设为 **`n`**。设为 `y` 时 SDIO 258 会直接 `esp_restart()` 造成 boot loop——对需要长期运行的中控面板是灾难。

**代价**
- 短期无法获得新版 hosted 的功能与修复
- 未来若必须升级，需要重新做一遍 SDIO 稳定性回归测试

**备注**：如果将来要升级，正确做法是：先做一版最小复现（只连 Wi-Fi + 持续 ping），跑 24 小时统计 SDIO 错误，再决定。**不要在主固件上直接试。**

**状态**：已接受（**已精确锁定 `==3.0.9` / `==1.6.5`**，2026-10-18）

## ADR-013 · F103 引脚全部继承现有工程，不做重排

**背景**：本项目 v1 的引脚表是我按芯片手册推测的，与前序工程实际接线**多处冲突**（MQ-4/MQ-135 对调、DHT11 在 PA8 而非 PB15、锁在 PB8 而非 PB14、蜂鸣器在 PB12 而非 PB9、PIR 在 PB13 而非 PB8 等）。

**决策**：**以现有工程的实际接线为准**，本项目不改引脚，`docs/04-硬件接线与BOM.md` §2 已按实测值重写。

**理由**
- 硬件已经焊好/插好并验证过，改引脚意味着重新接线，收益为零、风险为正（接线错误是这类项目最常见的故障源）。
- `USART1`(PA9/PA10) 本来就是"面向 ESP32"预留的，直接可用，**不需要为了协议而改任何引脚**。
- 把省下的时间用在真正缺的东西上（七项缺失能力）。

**代价**
- 保留了原分配的一些不理想之处（例如 ADC 全挤在 PA0~PA3）；PIR 已在本工程改为 **EXTI 中断**（PB13），不再是轮询
- 部分"更优布线"的想法被放弃——但这些优化收益很小，不值得动硬件

**状态**：已接受

## ADR-014 · 明确不复用前序工程的应用层（NES / 教育业务 / 云端 OCR）

**背景**：`smart-learning-box` 有大量成型的应用：NES 模拟器、K12 教育问答、拍照搜题 OCR、成就系统、错题本、游戏中心。

## ADR-015 · 分区表重排：从单分区改为双 OTA + coredump

**背景**：前序工程 `partitions.csv` 只有一个 `factory` app 分区（10MB），**没有 `ota_0`/`ota_1`、没有 `ota_data`、没有 `coredump`**。因此它**物理上无法做 P4 自身 OTA 与回滚**（它只有 C6 协处理器的固件推送机制），panic 时也拿不到调用栈。

**决策**：重排分区表，为**双 OTA 槽 + `ota_data` + `coredump` 分区**留出空间，并在阶段 8 输出一份 **Flash 地图文档**。

**理由**
- 中控面板是**装在墙上、长期运行**的设备。不能远程升级 = 每次改 bug 都要拆墙。
- 没有 `ota_data` 分区，连 `esp_ota_mark_app_valid_cancel_rollback()` 都不可用，"坏固件自动回滚"根本无从实现。
- 没有 coredump 分区，现场崩溃只能靠串口日志（前序工程的 `crash_log.c` 就是因此只打串口、不落盘）。
- 16MB Flash 完全够：当前 `factory` 占 **6MB**（`assets(fat)` 9900K 为预留），重排为双 OTA 槽仍有空间（实际固件体积需实测确认）。

**代价**
- 需要重新分配 `nvs`（现仅 24KB，偏小，配置+场景规则+版本记录都要放）、`slave_fw`（2MB，若不做 C6 固件推送可省）、`storage`（3.9MB FAT）
- 改动分区表会**清掉现有数据**，必须在阶段 8 一次性做完并重新烧录
- 连带需要确认 `esp_hosted` 的 C6 固件推送（`slave_fw` 分区）是否保留——保留则少 2MB 可用空间

**状态**：已接受但**尚未执行**，目标保留、**排后续阶段（阶段 8）**（不要提前动，避免和阶段 0~7 的开发反复烧写冲突）

## ADR-017 · 统一看门狗策略

**背景**：前序工程两处策略互相打架——`vision_core_init()` 把 TWDT 超时改成 60 秒，而 `font_loader.c` 又把 TWDT `deinit` 再 `init` 回 5 秒，**且在加载 7 个字体期间（约 44 秒）完全没有看门狗保护**。

**决策**：统一为以下策略，禁止 deinit：
| 场景 | 策略 |
|---|---|
| 常规运行 | 主任务注册 TWDT，超时 **10 秒**（不是 5s 也不是 60s） |
| 耗时操作（字体加载/OTA/图像初始化） | `esp_task_wdt_reconfigure()` **临时放宽到 60 秒**，完成后恢复，**全程不 deinit** |
| 关键任务监控 | 增加**任务看门狗**（协议收包 / UI / 网络），单任务卡死也能发现 |
| panic 行为 | `CONFIG_ESP_TASK_WDT_PANIC=n`（先重启 + 记日志，便于定位） |

**理由**
- `esp_task_wdt_deinit()` 是"关掉安全气囊"：如果在关闭期间卡死，系统永久挂起且无任何记录——比崩溃更难排查。
- `reconfigure()` 能达到同样的"临时放宽"目的，但**始终有保护**。
- 10 秒是折中：5 秒对字体/OTA 太紧，60 秒对常规运行太松（真卡死要等 1 分钟才发现）。

**代价**：需要梳理所有可能超 10 秒的操作并逐个处理（工作量不大但容易漏，列入阶段 0 验收）

**状态**：已接受

## ADR-018 · 动态天气壁纸采用 JWP 容器（而非 AVI/MJPEG 容器）

**背景**：天气动态壁纸最初按"每场景一段 MJPEG 封装进 AVI"设计（历史转换脚本已清理，1024×600@30fps）。参考工程
[ESP32-S3-LVGL-Clock](https://github.com/maxiumlee/ESP32-S3-LVGL-Clock)（Apache-2.0，HEAD `299ab2e6`）用的是自定义 **JWP** 容器：32 字节头 + 逐帧 baseline JPEG。需要决定跟哪条路。

**决策**：跟 JWP，理由：

| 维度 | JWP | AVI + MJPEG |
|---|---|---|
| 定位一帧 | `fseek` 到"长度字段 + 跳帧号 × 变长"（顺序读即可） | 需要解析 AVI 索引块（`idx1`）才能可靠跳转 |
| 循环回跳 | 头里一个 `transition_offset` 字段直接表达"片头只播一次" | AVI 无此概念，需应用层自己记帧号 |
| 校验 | 头里有 `payload_crc32`，转换脚本一次写入 | 无 |
| 播放器代码量 | 顺序读 + 解码（≈300 行） | 需要 AVI 解复用（≈double） |
| 素材来源 | 同一批 MP4/AVI 素材 → 同一套 ffmpeg 加工 | 同 |

JWP 是"为逐帧 JPEG 循环播放量身定做"的容器，几乎没有解复用成本；AVI 是通用容器，我们只用它装一条 MJPEG 流，代价却是要写一个 AVI 解析器。

**JWP 格式（固件 `standby/jwp_reader.c` 与 `ui/assets/scripts/make_wallpaper_jwp.py` 的唯一权威定义）**

```
offset  size  field
0       4     magic[4] = "JWP1"
4       2     version = 1
6       2     header_size = 32
8       2     width
10      2     height
12      2     fps_times_100   (fps × 100)
14      2     pixel_format    (1 = baseline JPEG)
16      4     frame_count
20      4     max_frame_bytes
24      4     payload_crc32   (zlib crc32，0 = 未计算)
28      4     transition_offset (循环回跳字节偏移，0 = 回到第一帧)
32…   重复 frame_count 次:  uint32 length + uint8 jpeg[length]
```
全部 little-endian。**只允许 baseline JPEG**（P4 硬件解码器与 esp_new_jpeg 都不支持 progressive）。

**目录结构（SD 卡）**
```
/sdcard/wallpaper/
├── sunny/    day.jwp  night.jwp
├── cloudy/   day.jwp  night.jwp
├── overcast/ overcast 维度的 day/night
├── rain/     day.jwp  night.jwp
├── storm/    day.jwp  night.jwp      (雷暴)
├── snow/     day.jwp  night.jwp
├── fog/      day.jwp  night.jwp
├── haze/     day.jwp  night.jwp
└── test/     sample.jwp              (入库的极小样例，18KB/3 帧)
```
场景名与 `weather_scene_to_string()` 一一对应（`storm` = 雷暴）。

**SD 卡容量要求**：按 1024×600、15fps、单帧 ≈ 60KB（质量 q≈4 的实拍素材）估算，
10 秒一段 ≈ 9MB；12 段（6 场景 × 昼夜）≈ 108MB。加上字体（≈10MB）与预留余量，
**建议 ≥ 1GB、FAT32、Class10/A1 以上**。仓库不提交这些大文件，只提交转换脚本 + `test/sample.jwp`。

**1024×600 性能限制**：参考工程是 480×360，参数不可照搬。实测依据（IDF 自测下限）：
P4 硬件 JPEG 解码 1080p→RGB565 ≥ **40fps**，而 1024×600 只有其 30% 像素量，
15fps 有充足余量；软件解码（esp_new_jpeg）作为回退，帧率待实测。
降级链路：`15 → 10 → 8 fps → 静态首帧 → 纯 LVGL 渐变背景`（`SMART_HOME_WALLPAPER_FPS` 可调）。

**许可与来源**：格式与"顺序读帧/循环回跳"算法移植自
`https://github.com/maxiumlee/ESP32-S3-LVGL-Clock`（Apache-2.0，HEAD `299ab2e63ea85f3463edc8fd8fd75142573c50fa`）。
**只移植格式定义与算法**，未复制其 Arduino 工程、播放器业务或天气代码；新增文件均带
SPDX 头与来源注释。解码改用 ESP-IDF 组件（`esp_driver_jpeg` 硬件 / `esp_new_jpeg` 软件），不引入 Arduino。

**状态**：已接受

## ADR-019 · 待机时钟层"叠加"在既有六页 UI 之上（不重写、不销毁）

**背景**：需要"天气动态壁纸 + 时钟待机界面"。当前已有六页智能家居 UI（`ui_pages.c`）并已在板上验收。

**决策**：
1. **不重写、不合并**六页 UI。待机层是 `lv_screen_active()` 的**最后一个子对象**，全屏
   `LV_OBJ_FLAG_CLICKABLE` —— 位于最上层并吞掉底层点击，等价于模态覆盖层。
2. 主 UI 与待机层**全程都不销毁**，只切换 `LV_OBJ_FLAG_HIDDEN`。切回不重建页面，
   避免 LVGL 对象反复创建/销毁带来的内存碎片与状态丢失。
3. **交互模型**：待机层显示时，**单击不唤醒**（防止误触），**双击**（窗口
   `SMART_HOME_STANDBY_DOUBLE_CLICK_MS`，默认 400ms）隐藏待机层并回到主 UI；
   主 UI 空闲 `SMART_HOME_STANDBY_IDLE_SEC`（默认 60s）无操作后自动回到待机层。
   任意触摸由 `LV_EVENT_PRESSED` 的 indev 级监听刷新"活跃时间"。
4. **启动顺序**：NVS → storage → crash_log → SD 卡 → Wi-Fi → LCD → 触摸 → LVGL →
   壁纸播放器（纯内存/无 LVGL）→ 主 UI + 待机层（`lv_async_call`，LVGL 任务上下文）→
   天气服务（后台任务）。**SD 必须在 Wi-Fi 之前**（Slot0/Slot1 共享时钟分频器，见 ADR-002 之前的实测结论）。
5. **跨任务边界**：`weather_service` 在天气任务里跑 HTTPS/SNTP，只通过
   `standby_ui_update_weather()` 写状态快照；LVGL 对象只在 LVGL 任务的 1s 定时器里更新。
   播放器帧通过 `frame_sink` 回调 + `lv_async_call` 进入 LVGL 上下文。
6. **网络失败行为**：不黑屏、不卡死、不阻塞。天气任务先加载 NVS 缓存点亮界面，
   再等 Wi-Fi（轮询，不占用 `wifi.c` 的单槽回调）→ SNTP → 拉数据；失败按
   60→120→240→…→900s 指数退避，界面保留 本地时间 + 缓存 + 上次选定的壁纸；
   完全没有缓存时用按本地时钟判断昼夜的**线性渐变兜底背景**。
7. **密钥不入库**：和风天气 Key/Location 只允许存在于 ①运行时写入 NVS
   （`storage_set_str("wx_key"/"wx_loc"/"wx_host")`）或 ②本地生成的 `sdkconfig`
   （已 gitignore）。Kconfig 默认值为空串，源码与 `sdkconfig.defaults` 里**永远不出现真实 Key**（延续 ADR-016）。
   （2026-10-09 修订：天气源切换为 uapis.cn；`wx_host` 已移除，`wx_key` 为 Bearer
   （未配置则只授时不请求）、`wx_loc` 可选——规则不变，见 ADR-020。）
8. **隔离测试开关**：`SMART_HOME_STANDBY_ENABLED` / `SMART_HOME_WALLPAPER_ENABLED` /
   `SMART_HOME_WEATHER_ENABLED` 三个总开关可单独关闭（关闭后对应模块编译为空实现，
   待机层自动回落渐变背景）；`SMART_HOME_STANDBY_SELFTEST` 打开后每 5s 打印一条
   自检日志（授时/天气/场景/Wi-Fi/可见性/解码帧率）；`SMART_HOME_WALLPAPER_TEST_FORCE`
   + `_TEST_SCENE` 可强制指定场景以绕过天气验证壁纸切换。

**代价**：待机层与主 UI 共用同一份字体资源与显示刷新（`ui_pages_font()` 暴露复用），
因此待机层的刷新会占用主 UI 的渲染预算；壁纸在待机层隐藏时暂停（`wall_pause()`）以让出带宽。

**状态**：已接受

## ADR-021 · 执行器单一所有权与命令仲裁

**背景**：F103 现有两条执行路径互不知情——自动灌溉（`app_irrigation.c`，500ms 周期，PB14 **低电平**吸合）与协议手动命令（`app_proto.c` 的 `actuator_execute()`，PB14 **高电平** ON）。极性相反且无互锁：手动命令会在 ≤500ms 内被灌溉判定覆盖。另有三处协议层缺陷：P4 影子在 ACK OK 时一律写 `state=1`（发 OFF 也显示 ON）、`ACTUATOR_STATUS` 回读帧 P4 不解析、F103 把 `ttl=0` 兜底成 2000ms（"持续开灯"2 秒后被自动关灭）。

**备选方案**
1. 维持双路径，"最近写入者获胜"——竞态仍在，只是从必现变偶发，不可接受
2. F103 建统一执行器管理器，所有写入（自动策略 / 协议命令）经它仲裁（**选定**）
3. P4 独占控制，删除 F103 灌溉逻辑——违反 ADR-001/009 故障域隔离，链路断开时无本地兜底

**决策**
1. F103 新增 `act_manager`：RELAY1 / RELAY2(=PUMP) / LOCK / BEEPER 收敛到单一状态机；`app_irrigation` 降级为"自动策略"，**仅在链路 LINK_DOWN 时接管灌溉判定**（延续 ADR-009 本地兜底模式）；LINK_UP 时灌溉由 P4 规则引擎（ADR-022）驱动。
   > ⚠️ **2026-10-18 实况（B2）**：上述"**本地灌溉兜底**"部分**未启用**——水泵实物未接，`APP_IRR_LOCAL_FALLBACK_ENABLE=0`，双阈值/干烧锁存逻辑被 `#if` 编译剔除；LINK_DOWN 时**仅强制关泵**（无本地双阈值兜底）。见 `docs/16` 决策 B2。
2. 极性收进 BSP 单点，应用层只见逻辑 ON/OFF，消灭"两处写同一 GPIO 且极性不同"。
3. 命令语义重定义：
   - **脉冲命令**（锁、蜂鸣器）：带 `ttl_ms`，到期自动回安全态；
   - **持久命令**（继电器/水泵）：`ttl=0` = 保持直至下一条命令，**不再默认 2000ms**；
   - **链路看门狗**：LINK_DOWN 持续 >10s → 执行器回 ADR-023 安全态（10s 容忍 UART 抖动，避免误关灯）。
4. 回读链路修复：F103 状态变化时主动上报 `ACTUATOR_STATUS`；P4 解析该帧更新影子；ACK 携带动作后状态而非恒 1。

**理由**：单一所有权是消除竞态的唯一干净方案；TTL 语义修正直接解决验收项"重启/断电安全态"的前置矛盾。（原"灌溉兜底保住 ADR-001 核心论据（P4 死机不停泵）"的表述已按 B2 撤回：水泵实物未接、本地兜底未启用。）

**代价**：F103 端 `app_irrigation`/`app_proto` 改动中等，需回归阶段 1 的 T-18 水泵超时锁存测试；P4 影子逻辑同步修改。

**状态**：草案（阶段四启动评审）；**已按实现复核（2026-10-18）**：单一 GPIO 所有权成立（`act_manager.c` 为 F103 唯一写路径），限时上限为 **泵 30s / 锁 1s / 蜂鸣 5s**（`ACT_MANAGER_PUMP/LOCK/BEEP_MAX_MS`），LINK_DOWN 持续 **>10s** 强制关断灯/泵/蜂鸣、锁保持安全态。

## ADR-022 · 本地规则引擎驻留 P4，NVS 双槽持久化

**背景**：验收要求"拔网线规则仍能本地触发"。本项目的"网"有两层：Wi-Fi（云端）与 P4↔F103 UART——拔 Wi-Fi 不影响 UART，规则引擎放 P4 即天然满足。P4 崩溃/重启时由 **ADR-023 安全态**保底（原计划的 F103 灌溉兜底未启用，见 `docs/16` 决策 B2）。现有 `storage.h` 只有通用 KV 接口，规则集需要结构化 blob + 校验 + 版本迁移。

**备选方案**
| 方案 | 评估 |
|---|---|
| 规则引擎放 F103 | 20KB RAM 跑不动通用规则集，且与既有灌溉兜底职责重叠 |
| 规则引擎放 P4，纯 C 可 PC 单测（**选定**） | 复用影子状态（ADR-005），不复制状态模型 |
| 双端各一份 + 同步 | 状态一致性复杂度不可控，违背"复用不复制"纪律 |

**决策**
1. P4 新增 `main/rule/rule_engine.{c,h}`：条件（传感器 dev_id + 比较器 + 阈值，最多 4 个 AND）/ 动作（执行器命令，最多 2 个）/ 优先级 / **去抖**（条件需持续成立 `debounce_ms` 才触发，边沿语义）/ **冷却**（`cooldown_ms` 内不重复触发）。评估周期 200ms，远小于 <200ms 延迟验收要求的影响路径（延迟测量只算 UI 点击→命令通道，不走规则引擎）。
2. **纯逻辑隔离**：时间（`now_us`）、传感器取值、命令下发全部经参数/回调注入，不 include 任何 ESP-IDF 头——`tests/` 下 PC 直接编译单测（沿用 `tests/f103-proto` 的 ctest 模式）。
3. 持久化：NVS 单 key blob = `magic("RST1") + version + crc32 + 固定布局 rule_set_t`（内联数组、无指针、静态断言防 padding）；**双槽写入**（先备份 key 再主 key，启动时主坏读备、双坏用默认模板）；版本迁移走逐版本函数链，未知高版本拒绝加载并告警。
4. 首发内置 5 条规则（**代码实测名**，全部 `enabled=0`，需 UI 显式开启）：**Arrive light**（PIR 有 → RELAY1 ON）、**Leave light**（PIR 无 → RELAY1 OFF）、**Smart watering**（土壤<35% 且雨滴<50 → 水泵 6s）、**Rain stop**（雨滴≥50 → 水泵 OFF）、**Quiet mode**（恒真 → 蜂鸣器 OFF）。UI 改动仅限规则启用开关与阈值输入，不得重做页面。

> 📌 **2026-10-18 实况核对**：持久化 namespace **已统一到 `"storage"`**（`STORAGE_NVS_NAMESPACE`；原自建 `"rules"` 已改，**旧数据作废**，首启写入默认规则），r0/r1/active 双槽键均在该 namespace 下，见 `docs/16` 决策 B7。

**理由**：与 ADR-004 本地优先一致；纯逻辑与硬件注入分离让"自动化单测"验收可直接 ctest 跑。

**代价**：blob 固定布局需 `_Static_assert` 防编译器 padding；双槽写多占约 1KB NVS（24K 分区足够，ADR-015 重排仍留阶段 8）。

**状态**：草案（阶段四启动评审）

## ADR-023 · 执行器失效安全状态表

**背景**：验收要求"P4 重启/断电时执行器回到定义好的安全状态，并论证安全状态是断开还是保持"。各执行器失效代价不同，不能一刀切。

**决策**（安全态表，唯一权威定义）：

| 执行器 | 上电默认 | 链路断开 >10s | P4 重启 | 整机断电 | 论证 |
|---|---|---|---|---|---|
| RELAY1 照明 | OFF | OFF | OFF（上电默认） | OFF | 灯意外点亮无安全收益，断开零代价 |
| RELAY2 水泵 | OFF | OFF + 30s 硬限时（T-18 已有，锁存语义） | OFF | OFF | 干烧/水淹是主要风险，断开是唯一安全侧；硬限时与软件看门狗互为双保险（ADR-010 模式） |
| LOCK 锁（**不接入**） | LOCKED | 保持当前态（默认锁定电平） | LOCKED | 物理保持 | ⚠️ **锁不接入**（实装模块买错，2026-10-18 删除 `app_lock`/`bsp_lock`，ADR-010 已废弃）；PB8 仍由 act_manager 独占写、默认锁定电平，本行仅保留安全态定义 |
| BEEPER | OFF | OFF | OFF | OFF | 持续鸣叫无意义，静音是安全侧 |

**"断开 vs 保持"判据**：失效动作是否可能造成物理伤害或财产损失——可能 → 断开（OFF）；断开本身有风险（锁）→ 保持。

**理由**：安全面必须有书面论证，这是 ADR-001 故障域隔离论据的完整闭环，也是面试深挖点。

**代价**：链路断开采用 10s 延迟关断而非立即关断（容忍抖动）；单测需断言该时序边界。

**状态**：草案（阶段四启动评审）；**已按实现复核（2026-10-18）**：LINK_DOWN 持续 >10s 强制关断灯/泵/蜂鸣，锁保持安全态（`act_manager_poll`），与 `ACT_MANAGER_PUMP_MAX_MS=30000` / `LOCK=1000` / `BEEP=5000` 一致。

## ADR-024 · C3 节点改用 BLE + MQTT 上行，不做 ESP-NOW 直连 P4

**背景**：路线图阶段六原定「C3 以 ESP-NOW 直连 P4，延迟 <20ms」。实际核对 P4 固件**没有 ESP-NOW 实现**；且 P4 的射频由板载 C6 经 `esp_hosted` 提供（ADR-008/012），要在 P4 上启用 ESP-NOW/BLE 需重烧 C6 协处理器固件，有搞挂现有 Wi-Fi 链路的风险。

**备选方案**
| 方案 | 优点 | 缺点 |
|---|---|---|
| ESP-NOW 直连 P4 | 延迟最低（<20ms）、无需 broker | 需重烧 C6 固件；P4 侧要新增收发与仲裁，风险与工作量都不可控 |
| C3 自己做 BLE + Wi-Fi/MQTT 上行（**选定**） | 不触碰 P4 射频；上行复用阶段五链路；手机可在无路由器时就近控制 | 延迟受连接间隔约束（30ms 量级）；两套射频分时共享 |
| C3 只做 BLE，由 P4 当 BLE 网关 | C3 固件最简单 | 仍要 P4 具备 BLE 主机能力（同方案 1 的风险） |

**决策**：方案 2。已在 2026-10-24 实测：BLE 连接（30ms）+ Wi-Fi + MQTT 共存 880s，Wi-Fi 0 掉线、`nfail=0`。

**理由**
- 不改 P4 射频固件，阶段五已验收的 MQTT/HA 链路直接复用，风险最小。
- 手机 BLE 直连让「配网」和「就近控制」都不依赖路由器与 broker，是电池节点的真实使用场景。
- BLE 的连接参数可主动申请（30ms），延迟口径可量化，比宣称一个做不到的 <20ms 更诚实。

**代价**
- 原验收「<20ms」作废，改为 BLE 30ms 连接间隔 + 1Hz Notify 的可复现口径（`docs/18` §6）。
- C3 承担两套射频，功耗与共存复杂度上升；broker 宕机时面板不可见（只剩 BLE 本地控制）。

**状态**：已接受

## ADR-025 · C3 SuperMini 天线失配：用 8.5dBm 限功率换取可用性

**背景**：C3 SuperMini 板载天线 2.4GHz 驻波比实测 5.81（社区网络分析仪数据），发射功率约一半被反射。表现为**收得到、发不出**：扫描 RSSI -43dBm 正常，但 AP 在 1 秒内收不到认证帧，节点反复 `AUTH_EXPIRE`（reason=2）。

**备选方案**
| 方案 | 可逆性 | 代价 |
|---|---|---|
| 保持满功率 20dBm | — | 实测关联必然失败，不可用 |
| **限功率 8.5dBm（选定）** | 软件可逆，Kconfig 一项 | 距离/穿墙能力下降 |
| 外置 FPC 天线 / 剪 IO20、IO21 | 硬件改动，剪脚不可逆 | 需重新做阻抗匹配；剪脚使两个 GPIO 报废 |
| 换品牌板/带外置天线版本 | 需采购 | 成本与供货不确定 |

**决策**：固件启动后调用 `esp_wifi_set_max_tx_power(34)`（单位 0.25dBm ⇒ 8.5dBm），配置项 `C3_WIFI_TX_POWER_QDBM`（8~84，填 80 恢复满功率）。

**理由**
- 实测在同一热点下：限功率前 `init→auth` 1002ms 后 `AUTH_EXPIRE`；限功率后 33ms 完成 `auth→assoc→run` 并拿到 IP，880s 无掉线。
- 不改硬件即可用，且保留一条 Kconfig 就能回到满功率做对照。
- 反射严重时降功率反而让信号“干净”，与社区多条实测一致。

**代价**
- 发射仅 8.5dBm，有效距离与穿墙能力明显弱于正常板；**跨房间部署不能靠软件解决**。
- 同款板批次差异大，本块可用不代表批量可用，采购前须抽测。

**状态**：已接受（同时记入 `docs/18` §7 已知限制）

## ADR-026 · Light-sleep 必须同时启用 BLE modem sleep，低功耗时钟用主晶振

**背景**：验收 8 首次尝试只开了「Wi-Fi modem sleep + 自动 light sleep」，未开 BLE 控制器 modem sleep。实测 2 分钟窗口内 BLE Notify 与 MQTT 同时中断一次，`seq` 缺 40 条（40 秒无上行）。IDF 文档明确：要保持 Wi-Fi/Bluetooth 连接，必须 **Wi-Fi 与 Bluetooth 都处于 modem sleep 且开自动 light sleep**，让驱动按需申请唤醒。

**备选方案**
| 方案 | 结果 | 代价 |
|---|---|---|
| 仅 light sleep（现状） | 双链路各断一次 | 不可用 |
| light sleep + BLE modem sleep，低功耗时钟 = **外部 32.768kHz** | 本板报 `32 kHz XTAL not found`，退回内部 RC | 晶振未起振，方案落空 |
| **light sleep + BLE modem sleep，低功耗时钟 = 主晶振（选定）** | 111s 采样 `seq` 全程连续；手机侧 Notify 未断 | 休眠时主晶振常驻，省电幅度小于 32k 方案 |

**决策**
```
CONFIG_PM_ENABLE=y / FREERTOS_USE_TICKLESS_IDLE=y
CONFIG_BT_CTRL_MODEM_SLEEP=y
CONFIG_BT_CTRL_MODEM_SLEEP_MODE_1=y
CONFIG_BT_CTRL_LPCLK_SEL_MAIN_XTAL=y
运行期 esp_wifi_set_ps(WIFI_PS_MIN_MODEM) + esp_pm_configure(light_sleep=true)
```

**理由**
- 官方文档给出的三条件是充分条件；补齐 BLE modem sleep 后，同一份代码、同一热点、同样 2 分钟口径下中断消失，属可复现对照。
- 主晶振（40MHz）在 IDF 文档中明确支持与 DFS、light sleep 共存；本板 32k 晶振实测不起振（§7-7），无更优时钟可选。

**代价**
- light sleep 期间 **USB-Serial/JTAG 关闭**：串口日志与常规烧录失效，须 BOOT 进 ROM 下载或改用外部 UART（GPIO20/21 + CH340）。
- 主晶振常驻，功耗高于 32k 方案；**实际电流未测**（验收 4），"省多少电"目前没有数字，不写入结论。

**状态**：已接受（验收 8 记为“功能层通过，功耗未测”）

## ADR-027 · 上行改 mqtts（自签 CA），keepalive 降到 12s

**背景**：阶段六收尾时两个真实缺口：
① 上行全部是明文 `mqtt://`，同一热点内的密码与传感器数据可被嗅探；
② LWT 掉线提示在 `keepalive=30s` 下要等约 45s（broker 按 1.5×keepalive 判超时），面板与 HA 的“离线”反应偏慢。

**备选方案**

| 方案 | 结果 | 代价 |
|---|---|---|
| 公开 CA（Let's Encrypt 等） | 需要公网域名 + 续期，本地热点场景不适用 | 无 |
| **自签 CA pinned（选定）** | `certs/ca.pem` 打进 mbedtls custom bundle，设备只信这一张 CA | 换 IP 需重签服务器证书；CA 私钥须由开发机保管 |
| 继续明文 + 仅内网 | 最简单 | 凭据与数据可嗅探，与 HA 侧安全口径不一致 |

| keepalive | `availability` 变 offline 的延迟 | 代价 |
|---|---|---|
| 30s（旧值） | **45s（实测）** | 掉线提示慢 |
| **12s（选定）** | 约 18s（broker 口径 1.5×12，待实测） | PINGREQ 更频繁，C3 light sleep 唤醒次数增加 |

**决策**
```
设备端：mqtts://<PC-IP>:8884，cfg.broker.verification.crt_bundle_attach = esp_crt_bundle_attach
        CONFIG_MBEDTLS_CUSTOM_CERTIFICATE_BUNDLE=y / PATH="certs"
broker：listener 8884（TLS，server.crt/key）+ listener 1884（明文，保留给 HA 与回退）
keepalive：CONFIG_C3_MQTT_KEEPALIVE_S=12 / CONFIG_SMART_HOME_MQTT_KEEPALIVE_S=12
```

**约束与代价**
- 证书由 `tools/gen_mqtt_certs.py` 生成；脚本**默认复用已有 CA**，只有首次才新建。
  换热点 IP 时只重签服务器证书（SAN），设备端 `ca.pem` 不变，**不必重烧**。
- 仓库只提交公开的 `certs/ca.pem`；`ca.key` / `server.key` 留在 `%TEMP%`，不入库。
- 明文 `1884` 仍开着属过渡态；生产应关闭，HA 也改走 8884。
- `keepalive` 12s 会让 C3 的 PINGREQ 频率翻倍，低功耗实测（验收 4）需按新值重测。

**状态**：已接受（2026-10-30），已实测：掉线检测 12s（旧值 30s 为 45s）；两端均以 TLS 连入 `:8884`
