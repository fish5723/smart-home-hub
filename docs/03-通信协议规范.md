# 通信协议规范 v2（P4 ↔ F103 ↔ C3）

> 版本 v2.1 ｜ 2026-10-18 ｜ 状态：**已实现**（阶段 2 完成，验收见 docs/13）
> 本文档是阶段 2 的核心交付物。**先写规范，再写代码**——顺序反过来就会变成"代码即规范"，加一个字段就崩。

---

## 1. 设计目标与约束

| 目标 | 具体指标 | 为什么重要 |
|---|---|---|
| 紧凑 | 帧头开销 ≤10 字节 | UART 115200bps 下每秒要传多个传感器值，JSON 会浪费 5~10 倍带宽 |
| 可检错 | CRC16 覆盖全帧 | 杜邦线环境噪声大，必须有比校验和更强的检错 |
| 可重同步 | 丢字节后能自己找回帧边界 | 长线缆/热插拔必然丢字节，不能一丢就永久失步 |
| 确定性 | 固定字节序、定长字段、两侧同源编码 | 链路只用定长 4B 的 **float32** 传测量值（§4.1）；F103 无 FPU，仅做 int→float 转换，协议层不做浮点比较 |
| 命令安全 | 指令带 TTL、执行后回读状态 | 防止"断线期间的旧指令"在恢复后突然执行 |
| 可扩展 | 版本号 + 能力位图 + 未知类型可忽略 | 以后加设备不用改协议版本 |
| 易调试 | 有 PC 端解析工具 | 没有工具，协议调试会退化成"盲猜字节" |

**物理层**：UART，TTL 3.3V，**115200 8N1**（阶段 2 起点；调试稳定后可提到 921600 并记录吞吐对比）。
**升级路径**：RS485（加 MAX485，抗干扰 + 长距离）或 TWAI/CAN（P4 有 TWAI 外设，F103C8 有 bxCAN，加 SN65HVD230）。协议帧格式不变，只换物理层。

## 2. 帧格式

### 2.1 总体结构（小端序 Little-Endian）

```
 偏移   字段          长度   说明
 ─────────────────────────────────────────────────────────────
  0     SOF           2B    帧起始 0xAA 0x55（固定）
  2     VER           1B    协议主版本号，当前 0x02
  3     TYPE          1B    消息类型（见 §3）
  4     SEQ           2B    序列号 0x0000~0xFFFF 循环
  6     LEN           2B    载荷长度（0 ~ MAX_PAYLOAD）
  8     PAYLOAD       LEN   载荷（可为 0）
  8+LEN CRC16         2B    CRC-16/CCITT-FALSE，覆盖 [VER .. PAYLOAD] 全部字节
 ─────────────────────────────────────────────────────────────
 最小帧长 = 10 字节（LEN=0 时）
 默认 MAX_PAYLOAD = 256 字节（F103 的 20KB RAM 约束下不宜再大）
```

**CRC 覆盖范围**：从 `VER` 到 `PAYLOAD` 末尾，**不包含 SOF 本身**。这样 SOF 只承担帧同步职责，不参与校验。

### 2.2 为什么这样设计（这些理由就是面试答案）

- **SOF 用 2 字节 `0xAA55` 而不是 1 字节**：单字节帧头在随机数据里平均 256 字节就会出现一次误判，双字节降到 65536 分之一，配合 CRC 几乎不可能误同步。
- **不做字节转义（不转义 0xAA/0x55）**：因为有了 `LEN` + `CRC`，收包状态机可以"按长度收、按 CRC 验"，校验失败就回到 `SOF` 位置向后搜索下一个 `0xAA55` 重同步。**代价是极端情况下需要扫描，收益是零额外带宽开销。**
  - 备选方案 `COBS`（一致性开销字节填充）确实能彻底消除帧头冲突，但会让载荷长度不定、增加 1 字节/254 字节开销与编解码复杂度。**本项目载荷固定、长度受控，故不采用。**
  - 💼 *面试可讲："我在两种重同步方案里做了取舍：COBS 更严谨但要改载荷长度并增加编解码开销；考虑到有线 UART 且帧长短，我选长度+CRC+重同步扫描。"*
- **CRC16 而非校验和**：校验和（8 位累加）检错率太差，无法发现字节交换等常见错误。CRC-16/CCITT-FALSE 能检出错发概率 <1e-5 级别的随机错误。
- **SEQ 16 位**：允许 65536 个在途消息，配合去重表足以覆盖重传窗口，且不会在 2s PING 保活下快速回绕。

### 2.3 CRC-16/CCITT-FALSE 算法

```
多项式  : 0x1021
初值    : 0xFFFF
输入反转: 否
输出异或: 0x0000
检查值  : CRC("123456789") = 0x29B1   ← 单元测试必须断言这个向量
```

实现建议（查表法，256 项表约占 512 字节 Flash）：
```c
static uint16_t crc16_ccitt(const uint8_t *buf, uint16_t len)
{
    uint16_t crc = 0xFFFF;
    while (len--) {
        crc ^= (uint16_t)(*buf++) << 8;
        for (int i = 0; i < 8; i++)
            crc = (crc & 0x8000) ? (uint16_t)((crc << 1) ^ 0x1021) : (uint16_t)(crc << 1);
    }
    return crc;
}
```
> 阶段 2 优化项：改成 256 项查表版本，实测每帧校验耗时下降多少（在 72MHz 上逐位算法约 8µs/字节，256 字节载荷就要 2ms+，**会成为瓶颈**）。

## 3. 消息类型表

命名规则：请求 `0xN0`，应答 `0xN1`；主动上报用独立段。

### 3.1 链路管理

| TYPE | 名称 | 方向 | 载荷 | 说明 |
|---|---|---|---|---|
| `0x01` | `HELLO_REQ` | 双向 | `ver(1B) + cap(4B位图) + fw_ver(4B)` | 上电/重连后首先发送 |
| `0x02` | `HELLO_RSP` | 双向 | `ver(1B) + cap(4B) + fw_ver(4B) + result(1B)` | `result`: 0=接受, 1=版本不兼容 |
| `0x03` | `PING` | 双向 | 空 | **保活帧**：HELLO 成功后由 P4 每 2s 发一帧，F103 收到即回 `PONG`（任何一侧收不到帧 → 3s `DEGRADED` / 6s `DOWN`） |
| `0x04` | `PONG` | 双向 | 空 | 对 PING 的应答 |
| `0x7E` | `NACK` | 双向 | `acked_seq(2B) + err_code(1B)` | 明确拒绝 |
| `0x7F` | `ERROR` | 双向 | `err_code(1B) + detail(2B)` | 异步错误上报 |

**能力位图（capability bitmap）**：位定义如下，用于"双方支持的设备/功能不同"时优雅降级。

| 位 | 含义 | 位 | 含义 |
|---|---|---|---|
| bit0 | 支持执行器控制 | bit8 | 支持日志上传 |
| bit1 | 支持气体传感器 | bit9 | 支持固件升级（IAP） |
| bit2 | 支持土壤/灌溉 | bit10 | 支持 CAN/RS485 物理层 |
| bit3 | 支持视觉事件 | bit11 | 支持配置读写 |
| bit4 | 支持场景引擎 | bit12 | 支持 ESP-NOW 节点转发 |

### 3.2 数据上报

| TYPE | 名称 | 方向 | 载荷 |
|---|---|---|---|
| `0x10` | `SENSOR_REPORT` | F103→P4 | 见 §4.1 |
| `0x11` | `SENSOR_REPORT_ACK` | P4→F103 | `acked_seq(2B)` |
| `0x12` | `ALARM_EVENT` | F103→P4 | 见 §4.2（**主动上报，无需请求**） |
| `0x13` | `ALARM_EVENT_ACK` | P4→F103 | `acked_seq(2B)` |

### 3.3 执行器控制

| TYPE | 名称 | 方向 | 载荷 |
|---|---|---|---|
| `0x20` | `ACTUATOR_CMD` | P4→F103 | 见 §4.3（**带 TTL**） |
| `0x21` | `ACTUATOR_CMD_ACK` | F103→P4 | 见 §4.4（**回读实际状态**） |
| `0x22` | `ACTUATOR_STATUS` | F103→P4 | 状态变化主动上报（如手动操作、保护触发） |

### 3.4 配置与运维

| TYPE | 名称 | 方向 | 载荷 |
|---|---|---|---|
| `0x30` | `CONFIG_GET` | 双向 | `key(2B)` |
| `0x31` | `CONFIG_SET` | 双向 | `key(2B) + len(1B) + value` |
| `0x32` | `CONFIG_DATA` | 双向 | `key(2B) + len(1B) + value` |
| `0x33` | `STATS_GET` / `0x34 STATS_DATA` | 双向 | 运行时统计（CPU/堆/重传率） |
| `0x50` | `LOG_FRAGMENT` | F103→P4 | `offset(4B) + total(2B) + data` |
| `0x60` | `OTA_BEGIN` | P4→F103 | `fw_size(4B) + crc32(4B) + version(4B)` |
| `0x61` | `OTA_DATA` | P4→F103 | `offset(4B) + data` |
| `0x62` | `OTA_END` | P4→F103 | `crc32(4B)` |
| `0x63` | `OTA_RESULT` | F103→P4 | `result(1B)` |

## 4. 载荷格式定义

**统一约定**：
- 全部整数为**小端序**，多字节量定长
- **测量值一律用 IEEE-754 `float32` 传输**（与两侧 `app_proto.c` 实现一致）。原设计曾要求"定点 `int32`、缩放 ×100、禁用 float"，但实现最终统一为 **float32**：F103C8 无 FPU，仅做 int→float 转换，协议层不参与浮点比较运算；float32 定长 4B、两侧同源（有 `_Static_assert` 兜底），跨平台语义明确。
- 每个传感器值带 **quality 字节**，表示数据可信度，见 §4.1。

### 4.1 `SENSOR_REPORT` (0x10)

```
num_entries (1B)
repeat num_entries 次:            // 每条固定 6 字节（SENSOR_ENTRY_SIZE = 6）
    dev_id   (1B)             设备/通道 ID，见 §5.1
    quality  (1B)             0=有效 1=预热中 2=超量程 3=传感器故障 4=陈旧数据
    value    (float32, 4B)    测量值（IEEE-754，小端）
```
> ⚠️ **条目不含 `type` 字段**——数据类型由 `dev_id`（§5.1）唯一确定；每条定长 6B（`dev_id(1)+quality(1)+float32(4)`），条目数受 `MAX_PAYLOAD` 约束。两侧实现严格同源：F103 `app_proto.c` 的 `APPEND_SENSOR` 与 P4 `app_proto.c` 的解析逐字段一致。
> ⚠️ 已知占位：`PROTO_DEV_BMP280_TEMP` 目前以 `quality=VALID` + `0.0f` 上报（BMP280 温度暂不单报），P4 面板会把 0.0 当有效值显示。
> **`quality` 字段是本协议最"企业级"的一个设计**。大多数 DIY 项目直接把 ADC 值当测量值上报，而真实产品必须区分"有效值"和"传感器还在预热/已经故障"。**MQ-135 上电后需要 24 小时老化**，这期间的数值必须标记为 `1=预热中`，否则会触发误告警。

### 4.2 `ALARM_EVENT` (0x12)

```
alarm_id  (1B)          告警源，见 §5.2（PROTO_ALARM_*）
level     (1B)          0=提示 1=警告 2=紧急（PROTO_LEVEL_*）
value     (float32, 4B) 触发值（与 SENSOR_REPORT 同口径）
threshold (float32, 4B) 阈值
（载荷合计 = 10 字节）
```
> ⚠️ **安全相关告警不由本协议决定是否告警**。气体超标时 F103 **本地直接响蜂鸣器**，本报文只用于"通知面板显示"。这是故障域隔离（ADR-009）在协议层的体现。
>
> **生产者与消费者（2026-10-18 落地）**：
> - **生产者（F103 `app_beep.c`）**：MQ-4/MQ-135 百分比 ≥60% 且 `quality==VALID`（与本地蜂鸣判定完全一致）→ **上升沿立即上报**，之后每 30s 节流重发；TX 槽被占（1Hz `SENSOR_REPORT` 在途）时挂起，`AppProto_Poll` 每轮重试（`AppProto_NotifyAlarm` / `alarm_retry_poll`）。
> - **消费者（P4 `app_proto.c`）**：解析进 `alarm_shadow_t` → `ESP_LOGW` 打印 → 回 `ALARM_EVENT_ACK`；**解除由数据判定** —— 收到对应设备（`0x01→PROTO_DEV_MQ4`、`0x02→PROTO_DEV_MQ135`）的新鲜有效数据且低于阈值时自动清 `active`。`AppProto_GetActiveAlarm()` 已就绪，面板/告警卡片上屏列入「阶段四补完」。
> - 安全动作（蜂鸣/关断）全部在 F103 本地完成，本帧只用于通知面板显示。

### 4.3 `ACTUATOR_CMD` (0x20)

```
dev_id   (1B)     执行器 ID，见 §5
action   (1B)     0=关闭 1=打开 2=脉冲(钛丝锁) 3=设定值 4=查询状态
param    (int32)  action=3 时的目标值（如水泵运行秒数）
ttl_ms   (2B)     命令有效期（毫秒）。接收端收到时若已超过发送时间+ttl_ms，则丢弃并回 NACK
```
> **`ttl_ms` 的意义**：假设链路断了 10 秒，P4 把"开水泵 30 秒"排进重传队列；如果没有 TTL，链路恢复后这条旧指令会突然执行。**给每一条控制指令加有效期，是工业控制的常规做法。** 对继电器 `ttl_ms=0` 表示保持直到下一条命令；水泵仍受 30 秒硬限时保护。蜂鸣器脉冲必须提供非零 TTL。
>
> **当前实现（2026-10-18）**：`ACTUATOR_CMD` 实际载荷为 `dev_id(1B) + action(1B) + pad(1B) + 发送时刻 ts(3B) + ttl_ms(2B) = 8B`（发送时刻供接收端做 TTL 判定），**尚未引入 `param(int32)`**；该字段为规范预留，后续扩展时保持前两字节兼容。

### 4.4 `ACTUATOR_CMD_ACK` (0x21)

```
dev_id      (1B)   执行器 ID
result      (1B)   0=成功 1=参数非法 2=设备忙 3=设备故障 4=安全联锁拒绝 5=TTL 过期
state       (1B)   执行后的**实际**状态（回读 GPIO，不是"我以为的状态"）
actual_param(int32) 执行后的实际参数
```
> **必须回读实际状态**：`result=成功` 只代表"指令被接受了"，`state` 才是"硬件真的动了"。继电器可能因过流保护没吸合，锁可能因卡死没开。**区分"指令确认"与"状态确认"是这类系统的分水岭。**

阶段四当前实现的 ACK 前缀为 `dev_id(1B) + result(1B) + state(1B)`；后续扩展
`actual_param(4B)` 时保持前三个字节兼容。

`ACTUATOR_STATUS (0x22)` 当前实现为：

```
count(1B)
repeat count 次: dev_id(1B) + state(1B)
```

该帧既用于状态查询响应，也由 F103 在本地兜底或安全保护导致状态变化时主动上报。

### 5.3 错误码（分层设计 —— 面试考点）

**传输层 `0x0X`**（链路/帧级问题）
| 码 | 含义 | 处理 |
|---|---|---|
| `0x01` | CRC 校验失败 | 丢弃该帧，统计 +1，**不回复**（回复会引发风暴） |
| `0x02` | 载荷长度非法 | 丢弃，回 NACK |
| `0x03` | 未知消息类型 | 丢弃，统计 +1（**不回复**，保证向前兼容） |
| `0x04` | 协议版本不兼容 | 回 NACK + ERROR，进入"不兼容"状态 |
| `0x05` | 接收缓冲满 | 回 NACK，请求重传（背压） |

**应用层 `0x1X`**（语义问题）
| 码 | 含义 | 处理 |
|---|---|---|
| `0x10` | 未知设备 ID | 回 NACK |
| `0x11` | 参数非法/超出范围 | 回 NACK（**并夹带合法范围**，便于调试） |
| `0x12` | 设备忙 | 回 NACK，调用方可稍后重试 |
| `0x13` | 设备故障 | 回 NACK + ALARM_EVENT |
| `0x14` | 安全联锁拒绝 | 回 NACK（如水泵正在运行时又收到启动指令） |

**执行层 `0x2X`**（硬件动作结果）
| 码 | 含义 |
|---|---|
| `0x20` | 执行超时 |
| `0x21` | 传感器未就绪（预热中） |
| `0x22` | 存储读写失败 |
| `0x23` | 状态回读与预期不符 |

> 💼 **为什么要分三层？** 因为定位问题的方式不同：传输层错误说明"线/干扰/波特率"有问题，应用层错误说明"设备没接或参数写错"，执行层错误说明"硬件真的坏了"。**面试时被问"你怎么定位通信问题"，这套分层就是答案。**

## 6. 可靠性机制

### 6.1 确认与重传
| 参数 | 定稿值 | 实测依据 |
|---|---|---|
| ACK 超时 | **100 ms** | 3.6h 压测 13064 帧 **0 次重传**（每次 RTT 均 <100ms）；115200bps 下 256B 帧传输约 22ms，100ms ≈ 4.5 倍余量 |
| 最大重传 | 3 次 | 超过则上报"控制失败"，UI 明确提示 |
| 重传退避 | 固定 100ms | 实测重传率 0%（目标 <0.1%），无收紧必要 |
| 需要 ACK 的类型 | `SENSOR_REPORT`·`ALARM_EVENT`·`ACTUATOR_CMD`·`CONFIG_*`·`OTA_*` | 即"有后果"的消息 |
| 不需要 ACK | `PING`/`PONG`（心跳本身即活性证明）、未知类型帧（回 ACK 无法处理） |

### 6.2 去重
接收端维护 **8 项环形去重表**（`{src, seq}`）。收到重复 SEQ：**丢弃载荷但重新回 ACK**（关键！否则对方会一直重传）。

### 6.3 心跳与链路状态机
```
保活机制（2026-10-18 按实现复核）：
- **HELLO 协商**：P4 每 2s 重试 `HELLO_REQ` 直到收到 `HELLO_RSP`（`HELLO_RETRY_MS = 2000`）。
- **保活**：HELLO 成功后 P4 每 2s 发 `PING`，F103 收到即回 `PONG`（F103 侧不主动发 PING，仅上电自检用一次）。
- **活性判定不依赖专门的心跳帧**：链路活性由"**收到任何有效帧**"证明（`SENSOR_REPORT` / `HELLO_RSP` / `PONG` / 任一业务帧均可刷新静默计时）。原 `PROTO_HEARTBEAT_MS` 常量定义后从未使用，**已删除（2026-10-18）**。

     ┌──────────┐  收到任意有效帧（含 HELLO_RSP）  ┌──────────┐
     │  LINK_   │ ──────────────────────────────→ │  LINK_UP │
     │  DOWN    │                                 └────┬─────┘
     └────┬─────┘                                      │ 3s 未收到任何有效帧
          │ 每 2s 重试 HELLO_REQ                       ↓
          └─────────────────────────────────────  ┌──────────┐
                                                  │  LINK_   │
        LINK_UP 期间任何有效帧都刷新静默计时       │ DEGRADED │
                                                  └────┬─────┘
                                            再 3s 无帧 │
                                                      ↓
                                               LINK_DOWN（UI 灰态 + 告警）
```
**参数定稿（2026-10-02 实测）**：

| 参数 | 值 | 依据 |
|---|---|---|
| 保活 / HELLO 重试周期 | 2s | 与 1Hz 上报叠加，正常静默窗口 ≤2s，阈值必须大于它 |
| UP→DEGRADED | 静默 3s | 拔线实测 28049ms 触发（最后收帧 +3s）；取"不误报的最小鲁棒值" |
| DEGRADED→DOWN | 再静默 3s | 拔线实测总检测 6s；UI 在 DEGRADED 已可提示，6s 才判死是权衡而非缺陷 |
| DOWN→UP（重连） | **实测 10ms** | 重插后首个到达帧即恢复（验收标准 <2s，余量 200 倍） |

**降级行为定义（必须实现，否则"断开"会变成"卡死"）**：
- `LINK_DOWN` 时：UI 上所有远端设备显示"离线"灰态，控制按钮禁用，**面板本身运行不受影响**
- `LINK_DOWN` 时：P4 保留最后一次已知状态并打上"陈旧"标记（不显示为实时值）
- F103 独立继续执行本地安全逻辑（气体告警、水泵超时）
- 链路恢复后：**P4 主动请求一次全量状态同步**（不能假设"状态没变"——断线期间 F103 可能被本地操作过）

### 6.4 版本协商
`HELLO_REQ` 携带 `ver`。规则：
- 主版本号相同 → 接受，启用能力位图交集
- 主版本号不同 → 回 `result=1`（不兼容）+ `ERROR(0x04)`，**双方都不再发送业务消息**（避免用错的格式互相污染）

## 7. 收包状态机

```
        ┌──────┐  收到 0xAA        ┌──────────┐  收到 0x55       ┌─────────────┐
        │ IDLE │ ─────────────────→ │ WAIT_SOF2│ ───────────────→ │ WAIT_HEADER │
        └──────┘                    └──────────┘                  └──────┬──────┘
            ↑                            │ 不是 0x55                    │ 收满 6 字节
            │                            └──────────┐                  ↓
            │                                       │           ┌─────────────┐
            │                                  （重同步）        │ WAIT_PAYLOAD│
            │                                                   └──────┬──────┘
            │                                                          │ LEN 字节收完
            │                                                          ↓
            │                                                   ┌─────────────┐
            │                                                   │  WAIT_CRC   │
            │                                                   └──────┬──────┘
            │                                                          │ 2 字节收完
            │                              CRC 失败 → 丢弃 + 统计 +1   ↓
            └────────────────────────────────────────────────  ┌─────────────┐
                                                                │  DISPATCH   │
                                                                └─────────────┘
```

**实现要点（这些细节决定了它能不能稳定跑 24 小时）**：
1. **不要在中断里解析协议**。ISR 只做：`HAL_UART_Receive_IT` 把字节丢进环形缓冲 / 或 DMA + IDLE 中断标记"一帧到达"，然后**投递信号量/队列，由任务去解析**。
2. **环形缓冲必须处理溢出**：缓冲满时丢弃最旧数据 + 计数上报（`0x05` 错误码），而不是覆盖未读数据导致状态机错乱。
3. **`LEN` 校验要早**：收到 `LEN` 立刻判断 `LEN <= MAX_PAYLOAD`，否则直接回 IDLE 重同步，**不要先分配缓冲再判断**（否则一个恶意/错误 LEN 就能撑爆 F103 的 20KB RAM）。
4. **超时保护**：状态机每个状态都要有超时（建议帧内字节间隔 >20ms 视为帧中断，回到 IDLE）——否则半帧会把状态机永久卡住。
5. **STATS 上报**：把 `rx_frames / crc_errors / retransmits / drops / resyncs` 都计数并通过 `0x33/0x34` 暴露出来。**没有这些统计，你无法回答"它稳不稳定"。**
