## 1. 准入门槛（阶段 1 的 4 项必修，全部完成才开工）

来自 `docs/11-阶段1-验收报告.md` §4。**其中第 2、3 项是阶段 2 的直接前置条件，不是可选项：**

| # | 门槛项 | 为什么卡阶段 2 |
|---|---|---|
| 1 | `main.c` 补 `#include "app_scheduler.h"`，构建归零警告 | 阶段 2 新增文件多，脏构建会掩盖真问题 |
| 2 | **DHT11 的 `delay_us(20000)` 移出 `__disable_irq()` 区间**（改为"先拉低引脚 → 出临界区 → 再延时"，或用 TIM 产生起始脉冲），把关中断窗口从 ~24ms 降到 ~4ms | **协议的超时判定依赖准确的 `HAL_GetTick()`**。当前 tick 系统性走慢约 1%，且每 2 秒有一个 24ms 的中断黑洞 —— 在这个黑洞里到达的 UART 字节会被推迟处理，直接破坏"帧内字节超时 20ms"的判定 |
| 3 | **复位原因打印接进启动流程**（`app_scheduler` 初始化时调 `BSP_IWDG_GetResetReasonStr()`） | 调协议时最常见的疑问是"刚才那次重启是协议 bug 崩的，还是看门狗复位？"没有这个输出就只能猜 |
| 4 | **Flash 降到 85% 以下**（当时 92.79%，仅剩 4.7KB）：排除 `bsp_ssd1306_tests.c`（3.5KB 死代码）+ 字体裁到 1~2 套（~15KB） | 协议栈需要 ≥6KB。装不进去就只能换 128KB 的 CBT6——那是个更大的动作（**✅ 已达成**：F103 Debug 实测 70.26%，见 §3.1） |

> 其余必修项（MQ ppm 恒 100、预热期参与告警、土壤断开误灌溉、干烧保护无限重启、`fault_cnt` 不清零）建议**与准入门槛同批改完再一起验证**，因为它们都在同一改动面上。它们不阻塞阶段 2 的代码编写，但会污染阶段 2 末尾的联调数据。

## 2. 写代码前必须定下的 5 个架构决策

### 决策 1（最重要）：协议收发绝不能排在主循环里

**问题（整改前）**：当时 `App_Scheduler_Run()` 是串行无抢占的顺序编排，最坏路径叠加可达 400ms 级（DHT11 24ms + OLED 整帧 25~90ms + BMP280 I2C 超时 100ms + OLED 逐页 50ms×8）。
**后果**：协议要求 ACK 超时 50ms（**最终定稿 100ms**）、重传 3 次、帧内字节超时 20ms。如果收包/ACK 排在 OLED 刷屏之后，**对端早就判定超时重传了**，协议在纸面上正确、在现场完全不工作。

**决策**：USART1 侧走 **DMA + IDLE 中断**，且**不在中断里解析**：

```
USART1 RX → DMA1_Channel5（循环模式）→ 环形缓冲
                    ↓
         IDLE 中断（一帧结束，总线空闲 ≥1 字符时间）→ 置标志 / 投递事件
                    ↓
             协议任务（独立，不是主循环里的一个 Task）
```

- **ISR 只做两件事**：记录 DMA 当前写入位置、投递信号量。**绝不在 ISR 里解析帧、做 CRC、发 ACK、打印日志。**
- 收包状态机与 CRC 校验放在协议任务上下文。
- 若阶段 2 暂不引入 RTOS：至少也要让**收包解析与 ACK 发送**成为一个"高优先级轮询段"，排在传感器轮询之前，并用 DMA 保证字节不丢。

**这与 `docs/02-系统架构.md` 里"F103 用裸机还是 FreeRTOS"的待决策项直接相关** → 建议在阶段 2 的第 1 周内用实测数据决定，判据是：DMA+IDLE 收包 + 协议任务与现有 11 个任务的时序是否互相干扰。

### 决策 2：F103 的 DMA 通道分配（不能随便选）

STM32F103 的 DMA1 通道与外设是**硬件固定映射**的：

| DMA1 通道 | 已占用 | 阶段 2 用途 |
|---|---|---|
| Channel 2 | ✅ 已给 **USART3_TX**（retarget 用，`Core/Src/dma.c:39-49`） | 保留 |
| Channel 4 | 空闲 | **USART1_TX**（协议发送，推荐用 DMA 以免 ACK 被其它任务拖延） |
| Channel 5 | 空闲 | **USART1_RX**（协议接收，必须用） |
| Channel 1 | 空闲 | ADC（阶段 2 不需要，留给以后提高采样率） |

**注意**：`Core/Src/dma.c` 是 CubeMX 生成的，新增通道要在 CubeMX 里配好再生成，否则下次重新生成会覆盖。

### 决策 3：两个串口的分工要在代码里固化

| 串口 | 引脚 | 用途 | 约束 |
|---|---|---|---|
| **USART1** | PA9 / PA10 | **只跑协议**（二进制帧） | 不允许出现任何 `printf`/ASCII 文本。一旦混入裸文本，PC 端解析工具就没法区分"帧"和"调试噪声" |
| **USART3** | PB10 / PB11 | 调试 `printf`（retarget，已配 DMA 环形缓冲） | 保持纯文本，供人看 |

**为什么必须分开**：现在调试输出和协议若共用一个口，抓包时会看到二进制里夹着 ASCII，无法自动解析。分开之后，逻辑分析仪接 PA9/PA10 能抓到干净帧。

### 决策 4：ACK 超时别照抄 50ms，先用实测数据定

`docs/03-通信协议规范.md` 写的是 ACK 超时 50ms（理由是 115200bps 下 256 字节帧约 22ms，留 2 倍余量）。这个推导本身没问题，但**当前实现的最坏响应延迟是数百毫秒**（见决策 1）。

**建议做法**：
1. 阶段 2 先用 **100ms** 作为初始 ACK 超时，把参数做成**可运行时修改**（便于做参数扫描）
2. 修完决策 1 之后，实测**端到端往返延迟分布**（不是平均值，要看不含异常的 P99）
3. 按实测数据把超时收紧到 `P99 × 1.5 ~ 2`，并把测量数据写进协议文档
   → 这样"超时为什么是 X ms"就是有数据支撑的结论，而不是抄来的数字（**这正是面试会追问的地方**）

> **结论（定稿）**：最终 `ACK_TIMEOUT` 保持 **100ms**（与 `docs/03-通信协议规范.md` §6.1 一致）。3.6h / 13,064 帧压测实测 **0 重传**，无需继续收紧；"别照抄 50ms"的论证仍成立 —— 100ms 是由主循环实测延迟推出的，而非照抄规范值。

### 决策 5：时间基准要分两级

| 用途 | 基准 | 说明 |
|---|---|---|
| 协议超时、重传窗口、心跳周期 | **ms 级：`HAL_GetTick()`** | 前提是门槛 2 已修，tick 不再漂移 |
| 帧内字节超时（20ms）、位时序 | **µs 级：TIM 基准** | 当前只有 DWT 忙等（`Sys/delay.c`），建议在阶段 2 顺手把它换成 TIM 基准 |

**顺带收益**：把 DWT 忙等换成 TIM 基准，同时就完成了阶段 1 遗留的 T-09 的"微秒延时改 TIM 基准"这一半。

## 3. 资源预算（先算清再动手）

### 3.1 F103C8T6（20KB RAM / 64KB Flash）

**RAM**：当前已用 6,528 B（31.88%），余 13.9KB。协议栈预算：

| 项 | 预算 | 说明 |
|---|---|---|
| RX 环形缓冲 | 512 B | 够放 2 个最大帧（256B）还留余量 |
| TX 缓冲 | 256 B | 单帧最大载荷 |
| 去重表 | 24 B | 8 项 × `{src, seq}` |
| 统计结构 | 32 B | rx_frames / crc_errors / retransmits / drops / resyncs |
| 协议状态机 + 标定表 | ~200 B | |
| **合计** | **≈ 1 KB** | **完全够用**，RAM 不是瓶颈 |

**Flash**：当前 60,808 B / 92.79%，只余 4.7KB。协议栈预算：

| 项 | 预算 |
|---|---|
| CRC16-CCITT 查表（256 项 × 2B） | 512 B |
| 收发状态机 + 组包/解包 | ~2 KB |
| 消息处理分发 | ~1 KB |
| 统计与错误码字符串 | ~0.5 KB |
| **合计** | **≈ 4~6 KB** |

→ **结论：Flash 必须先瘦身（门槛 4），否则协议装进去就没余量做阶段 8 的 IAP。**

> **（2026-10-18 复核实测）**：上面 RAM 6,528 B（31.88%）与 Flash 60,808 B（92.79%）是阶段 2 开工时快照；F103 Debug 当前实测 **FLASH 46,044 B / 64 KB = 70.26%，RAM 8,584 B / 20 KB = 41.91%**（见 docs/11 §1.2 与 docs/15），瘦身已完成。本文 §1 门槛 4 与 §3.1 的旧数字均以此为准。

### 3.2 P4 侧

P4 有 16MB Flash / 32MB PSRAM，**资源不是问题**。真正的约束是：
- `docs/03-通信协议规范.md` 的帧格式要在两侧**各自独立实现**（不共用代码，这是"协议"而非"库"的证明）
- P4 侧已有的 `bsp/storage`（NVS）可直接用于协议统计的持久化

## 4. 阶段 2 的任务分解（建议三批推进）

### 批次 2A · 先打通"PC ↔ F103"（约 3~4 天）

> **核心方法：用 PC 当对端**。在 P4 侧协议栈写好之前，先用 PC 脚本当"假 P4"来验证 F103 侧收包与组包 —— 这样两侧的 bug 不会互相掩盖。这是本阶段最省时间的调度决策。

| 编号 | 任务 | 产出 |
|---|---|---|
| 2A-1 | CubeMX 配 USART1 的 DMA1_Ch4/Ch5 + IDLE 中断；建 RX 环形缓冲 | `Core/` 配置 + `APP/comm/proto_rx.c` |
| 2A-2 | 收包状态机（`IDLE→SOF1→SOF2→HEADER→PAYLOAD→CRC→DISPATCH`）+ 帧内字节超时 | 能正确切出一帧 |
| 2A-3 | CRC16-CCITT 查表实现 + 生成 256 项表 | 断言 `CRC("123456789")=0x29B1` 通过 |
| 2A-4 | 组包（SOF/VER/TYPE/SEQ/LEN/PAYLOAD/CRC）与发送（DMA） | 能发出合法帧 |
| 2A-5 | `APP/comm/proto_tx.c`：ACK 超时 + 重传（最多 3 次）+ 序号去重表 | 收不到 ACK 会重传 |
| 2A-6 | 心跳（1Hz PING/PONG）+ 链路状态机（UP/DEGRADED/DOWN） | 拔线后进 DOWN，插回后恢复 |
| 2A-7 | **`tools/protocol_sniffer.py`**：录包 → 解析成表格 → 统计（帧数/CRC 错误/重传/重同步次数） | PC 侧可视化 |
| 2A-8 | **PC 端假 P4 脚本**（`tools/fake_peer.py`）：按规范回 ACK / 发命令 / 造错帧 | 用于压 F103 侧的容错路径 |

**2A 验收**：PC 脚本发一条 `ACTUATOR_CMD`，F103 真实驱动继电器并回带实际状态的 ACK；PC 端统计显示 0 丢包。

### 批次 2B · P4 侧协议栈 + 双芯真实联调（约 4~5 天）

| 编号 | 任务 | 产出 |
|---|---|---|
| 2B-1 | P4 侧协议栈**独立实现**（ESP-IDF UART 驱动 + `uart_event_t` 或自建 DMA/DLE 收包） | `components/protocol/` |
| 2B-2 | P4 侧设备抽象挂在协议之上（阶段 3 的铺垫：先做最小的"设备影子"） | 能读到 F103 上报的传感器值 |
| 2B-3 | 两端联调：心跳、全量状态同步、命令下发 | 端到端跑通 |
| 2B-4 | 版本协商（`HELLO`/`HELLO_RSP` + 能力位图）与不兼容处理 | 版本不匹配能优雅拒绝 |
| 2B-5 | 指令 TTL 校验（防断线恢复后执行旧指令） | 过期指令被拒且回 NACK |
| 2B-6 | 收紧 ACK 超时到实测值（决策 4） | 参数 + 实测数据写进协议文档 |

**2B 验收**：面板（或 P4 串口）点击 → F103 继电器动作 → 状态回读，端到端延迟有实测数据。

### 批次 2C · 可靠性验证与固件化（约 3~4 天）

| 编号 | 任务 | 产出 |
|---|---|---|
| 2C-1 | **单元测试**（PC 上跑，不依赖硬件）：CRC 标准向量、半包、粘包、超长帧、错帧、非法类型、重复 SEQ、TTL 过期 | `tests/`，`ctest` 一键跑 |
| 2C-2 | **故障注入**：比特翻转 1000 次 + 丢字节 1000 次，要求全部被 CRC 检出且零误执行 | 测试报告 |
| 2C-3 | **24 小时压测**：10Hz 上报 + 1Hz 心跳，统计丢包率与重传率 | 统计输出 + 数据表 |
| 2C-4 | **物理层故障**：运行中拔插杜邦线、TX 短接到地、在电机工作时观察误码 | 断线重连 <2s 的证据 |
| 2C-5 | 协议文档定稿（含实测参数、错误码、时序图） | `docs/03` v2.0 正式版 |

**2C 验收 = 阶段 2 验收**（沿用路线图）：
- 24h 压测丢包率 **0**、重传率 **<0.1%**
- 故障注入 1000 次全部检出、零误执行
- 单元测试覆盖上述 8 类场景，`ctest` 全绿
- 拔线后重连 <2s，且**不产生半条指令导致执行器误动作**

- [ ] **逻辑分析仪接线**：至少接 PA9(USART1_TX) / PA10(RX) / GND 三根。抓帧时用它同时看两端的 TX，比对时序

- [ ] **两端电平确认**：都是 3.3V TTL，直连即可（不需电平转换）

## 6. 阶段 2 的主要风险

| 风险 | 表现 | 规避 |
|---|---|---|
| **主循环延迟破坏协议时序** | 协议纸面正确但现场丢包/重传爆炸 | 决策 1：收包与 ACK 脱离主循环 |
| **tick 漂移**（阶段 1 遗留） | 超时判定随机偏移，压测数据不可信 | 准入门槛 2 |
| **Flash 不足** | 协议装进去后余量归零，阶段 8 的 IAP 无法做 | 准入门槛 4 |
| **调试口与协议口混用未固化** | 抓包看到二进制里夹 ASCII，无法自动解析 | 决策 3 |
| **两侧 bug 互相掩盖** | P4 与 F103 都刚写完，出问题不知道怪谁 | 批次 2A：先用 PC 当对端把 F103 侧单独验干净 |
| **ACK 超时照抄规范值** | 台上调不通、台下反复调参 | 决策 4：先实测再定 |
| **协议代码与 HAL 耦合** | 单元测试写不出来，只能靠硬件跑 | 2A-1 就把纯逻辑层与 HAL 层分开 |
