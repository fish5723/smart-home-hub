# 19 · 阶段七 · 端侧视觉规范（人脸检测）

> 口径：本阶段做的是**人脸检测（Human Face Detection）**，不是人脸识别/身份认证。
> 所有数据均为本机实测，未测项会明确标注「未测」。

## 1. 硬件与平台约束

| 项 | 值 | 来源 |
|---|---|---|
| 主控 | ESP32-P4，芯片 rev **v1.3** | 启动日志 `chip revision v1.3` |
| 摄像头 | OV5647，MIPI-CSI 2-lane，800×640@50fps RAW8 | `esp_cam_sensor` 格式表 |
| CSI 颜色转换 | **rev<3.0 不支持**，CSI 只能 RAW8→RAW8 直通 | `esp_cam_ctlr_csi.c` 版本门限 |
| ISP | 支持 RAW8→RGB565；**WBG（白平衡）在 rev<3.0 返回 `ESP_ERR_NOT_SUPPORTED`** | `isp_wbg.c` 版本门限 |
| 帧格式 | ISP 输出 RGB565 整帧 1,024,000 字节（800×640×2） | 运行日志 |
| JPEG | P4 硬件编码 + 解码均可用（`esp_driver_jpeg`） | `jpeg_encode.h` / 实测 |
| 软件 JPEG | `espressif/esp_new_jpeg`（纯 CPU） | `idf_component.yml` |

### 1.1 P0 摄像头链路修复结论（已提交 `cd66b22`）

问题根因按发现顺序：

1. CSI 请求 RAW8→RGB565 被驱动拒绝 → 改为 CSI 直通 RAW8，由 ISP 转 RGB565。
2. 抓帧即 panic → ISR 里做 512KB `memcpy`；改为 ISR 只记录缓冲指针，拷贝移到任务上下文。
3. 一帧都收不到 → 帧缓冲未按 PSRAM cache line 对齐（`esp_cache_get_alignment`）、
   缓冲尺寸按 RAW8 算（512,000）、传感器开流时机不对；按 IDF `test_apps/csi` 对齐后修复。
4. 有帧但黑白 → ISP 仅启用基础管线，且 Bayer 相位未设置；启用 BF/demosaic/gamma +
   `COLOR_RAW_ELEMENT_ORDER_GBRG` 后恢复正常彩色。

实测（清理版固件，启动自检抓 3 帧）：

| 帧 | 结果 | 耗时 | 缓冲 |
|---|---|---|---|
| 1 | ESP_OK | 54.1 ms | 1,024,000 B |
| 2 | ESP_OK | 24.9 ms | 1,024,000 B |
| 3 | ESP_OK | 25.2 ms | 1,024,000 B |

## 2. 验收 1 · JPEG 硬件编码 vs 软件编码

**方法**

1. 启动时抓一帧 RGB565（800×640，1,024,000 B）作为快照；
2. 同一帧分别用硬件编码器（`esp_driver_jpeg`）与软件编码器（`esp_new_jpeg`）编码，
   各跑 **5 次**，取耗时中位数；
3. 两条码流用 **硬件解码器**（RGB565、BGR 元素序、BT601）解回并与原帧算 PSNR；
4. 质量统一 80，YUV420 子采样。

**结果（quality=80）**

| 指标 | 硬件编码 | 软件编码 |
|---|---|---|
| 5 次耗时中位数 | **7.67 ms** | **216.7 ms** |
| 输出码流 | **23,073 B** | 24,976 B |
| 解码回 RGB565 | 成功 | 成功 |
| 回放 PSNR（原帧 vs 解码） | 25.0 dB | 25.0 dB |

**解读**

- 硬件编码约为软件编码的 **28×**，单帧 7.7 ms → 满足 30fps（33 ms/帧）预算。
- 两者码流大小接近（差 8%），说明硬件编码质量与软件实现相当。
- PSNR 24.9 dB 偏低，原因是**输入帧本身噪声很大**（低照度下 AEC 把增益拉到 ~15×，
  曝光已到 50fps 模式上限），JPEG 对噪声编码误差会被放大；这是源图像问题，
  不是编码器缺陷。后续 P3 用灰度/降噪后再评估。
- 复现：`main/vision/jpeg_bench.c`，启动日志关键字 `[JPEG] HW ok=1 dec=1 ...`。

## 3. 验收 2（上半）· PC 端 FP32 基线

### 3.1 模型选型的既成事实

先查了官方渠道，结论是**拿不到与端侧同网络的浮点权重**：

| 检查项 | 结果 |
|---|---|
| `esp-dl/models/human_face_detect/models/p4/` | 只有 4 个 `.espdl`（`human_face_detect_msr_s8_v1`、`mnp_s8_v1`、`espdet_pico_224/416_face`） |
| `esp-detection` 仓库 | 只提供猫检测的 `.pt`，没有人脸预训练权重 |
| `esp-ppq` | 只有 ONNX → `.espdl` 单向导出，无反向 |

因此改为「**公开 FP32 参照**」口径：PC 侧用 OpenCV Zoo 的 **YuNet（2023mar，FP32 ONNX）**，
端侧 P3 仍用 esp-dl 的 MSR+MNP INT8。**两者不是同一个网络**，本表只做任务级参照，
不用于推导「量化损失」；这条限制在 P3 数据出来后同样成立。

### 3.2 测试集（50 张，不入库）

| 类别 | 数量 | 来源 | 许可 |
|---|---|---|---|
| 正样本（含人脸框） | 40 | WIDER FACE **validation** 子集（`CUHK-CSE/wider_face` 镜像） | CC BY-NC-ND 4.0 |
| 负样本（无脸室内场景） | 10 | Wikimedia Commons，标题为 `Empty apartment/room/office` 的空房间照片 | 各图许可见 `negatives.json` |

选择规则（脚本内固定，可复现）：每张正样本 1~4 张人脸、最小边 ≥ 40 px、
同一 WIDER 事件目录最多 2 张（保证场景多样），共覆盖 20 个事件目录。
负样本逐张目视确认无人脸（联系表人工核验）。

> 数据集与 WIDER 原始压缩包都放在 `tools/vision/data/`（已 git-ignore），
> 不随仓库分发；重复评测时脚本会重新拉取。

### 3.3 方法

1. 预处理：原图等比缩放到 640×640，右下补零（letterbox），BGR、float32 原值（0~255，模型内无归一化算子）；
2. 推理：onnxruntime `CPUExecutionProvider`，`intra_op=4`、`inter_op=1`，图优化全开；
3. 后处理：按 stride 8/16/32 解码，`score=sqrt(cls*obj)`，NMS IoU 0.3，框映射回原图坐标；
4. 匹配：预测框按分数贪心匹配 GT，IoU ≥ 0.5 记 TP；未匹配且与任何 WIDER 原始人脸框（含
   被 40 px 规则过滤掉的小脸）IoU ≥ 0.3 的检测记为 **ignored**，不计入误检；
5. 负样本上任何检测都算 FP；
6. 耗时：同一帧预热 3 次后连跑 20 次，取中位数；内存：进程 `peak_wset`（含解释器与模型加载）。

### 3.4 结果

| 指标 | score ≥ 0.6 | score ≥ 0.9 |
|---|---|---|
| TP / FN / FP / ignored | 77 / 4 / 18 / 119 | 40 / 41 / 0 / 10 |
| 负样本误检（10 张） | **0** | **0** |
| 精确率 / 召回率 / F1 | **0.811 / 0.951 / 0.875** | 1.000 / 0.494 / 0.661 |
| 检测框总数（50 张） | 214 | 50 |
| 单帧推理中位数（PC CPU） | **3.62 ms** | 3.62 ms |
| 进程峰值内存（加载后） | 131.4 MB（增量 65.6 MB） | 131.4 MB |

其他固定量：模型 232,589 B，输入 640×640×3，会话加载 ~1.5 s（含图优化，PC 侧一次性开销）。

**解读**

- 0.6 阈值下召回 95%、负样本 0 误检；18 个 FP 中多数是 WIDER 未标注的极小背景人脸，
  说明模型本身没有明显「乱框」倾向。
- 0.9 阈值（OpenCV 默认）召回跌到 49%，对人脸占比小的 800×640 取景画面过于保守；
  **P3 端侧默认取 0.6**，并在 P4 用 PIR 触发距离再调。
- 3.62 ms 是桌面 CPU 的数字，**不能与 P4 的 INT8 耗时直接对比**（列成两列只为后续并表）。

### 3.5 复现

```
python tools/vision/fetch_yunet.py                 # 下载模型（sha256 校验）
python tools/vision/fetch_wider_subset.py          # 40 张正样本 + labels.json
python tools/vision/fetch_negatives.py             # 10 张负样本
python tools/vision/bench_fp32.py --score 0.6 --runs 20
python tools/vision/bench_fp32.py --score 0.9 --runs 20
```

## 4. 验收 2（下半）· 端侧 INT8 人脸检测（P3）

> **2026-11-07 模型选择说明**：`face_detect.cpp` 已改为按 Kconfig 在
> `MSRMNP_S8_V1` 与 `ESPDET_PICO_416_416_FACE` 之间切换。
> **产品默认取 ESPDet（召回优先）**；MSRMNP 作为低延迟备选（实测 avg 20.6 ms、
> recall 0.210）。§4.3/§4.4 的 18.6–24 ms、0.3 阈值现场复核数据来自 MSRMNP；
> §4.7 给出两种模型在同一测试集上的框级对比。

### 4.1 集成方式

| 项 | 值 |
|---|---|
| 依赖 | `espressif/esp-dl ^3.3.14` + `espressif/human_face_detect ^0.5.2`（registry 解析通过） |
| 模型 | `MSRMNP_S8_V1`（两阶段，INT8），Kconfig 默认 `flash_rodata` 嵌入 |
| 模型字节 | 61,248 B（MSR）+ 129,968 B（MNP）= **191,216 B** |
| 封装 | `main/vision/face_detect.cpp`（C++ → `extern "C"`），输入 ISP 的 RGB565LE 整帧 |
| IDF 兼容 | IDF 6.1 + esp32p4 **直接编译通过**，未改动组件源码（仅 `idf_component.yml` + CMake `REQUIRES`） |

### 4.2 资源占用

| 项 | 值 |
|---|---|
| app 镜像 | **4,752,064 B**（集成前 2.50 MB 量级）；6 MB 分区余 **1,535,808 B（24%）** |
| 模型常驻 PSRAM | **415,368 B**（26,401,828 → 25,986,460，第一次 run 时加载） |
| 说明 | 模型惰性加载：`face_detect_init()` 不占 PSRAM，首次推理才分配 |

### 4.3 单帧耗时（P4 @360 MHz，800×640 → 模型内部 160×120，0.3 阈值）

| 场景 | 耗时 |
|---|---|
| 首次推理（含模型加载） | **82.3 ms** |
| 后续，无候选 | **18.6 ~ 19.4 ms** |
| 后续，检出 1 张脸 | **24.0 ms**（0.2 阈值实测） |

比厂商 README（P4@400 MHz：MSR 12.4 ms + MNP 2.3 ms/候选）偏慢，差异来自
360 MHz 主频、默认 `-Os` 优化、以及 800×640→160×120 的缩放预处理。

### 4.4 检测有效性验证

| 测试 | 结果 |
|---|---|
| 真人站在画面右侧，阈值 0.2 | `count=1 best=0.516 box=(631,294,156,214)` —— 框位置与肉眼所见一致 |
| 同一场景，厂商默认 0.5 | `count=0` —— **漏检** |
| 画面无人，0.3 / 0.5 阈值 | `count=0`（十余次抓帧），无异常、无 panic |

结论：链路（RGB565→预处理→MSR→MNP→坐标回映射）正确；厂商默认 0.5 对当前
低照度画面偏严，默认改为 **0.3/0.3**。

> **0.3 阈值的现场复核已完成（2026-11-02，P4 事件内）**：同一站位下 frame2/3 检出
> `count=1 score=0.56 / 0.53`，角标显示 `FACE 1 0.56`；无人时为 `NO FACE`（3/3 帧）。

### 4.5 与 PC FP32 基线的对比口径

| 项 | PC（YuNet FP32） | P4（INT8，当前 ESPDET 416） |
|---|---|---|
| 网络 | YuNet（单阶段） | MSR + MNP（P3 旧版）→ ESPDET PICO 416（当前）—— **不是同一网络** |
| 精度 | 40 正 + 10 负：recall 0.951 / precision 0.811 | **同一测试集已测（ESPDET 416，见 §4.7；MSRMNP 版本未测）** |
| 单帧耗时 | 3.62 ms（桌面 CPU） | MSRMNP 18.7 ~ 24.0 ms；ESPDET 416 **225 ~ 230 ms** |
| 内存 | 进程峰值 131.4 MB | MSRMNP 模型 415 KB（PSRAM）；当前 app 3.35 MB，分区余 47% |

**因此本阶段仍不能给出「量化损失」结论**：两端网络不同、NMS 口径不同。P3 交付的是
「端侧可运行 + 资源/耗时实测」；ESPDET 416 已完成同批图的任务级对比（§4.7），
MSRMNP 版本尚未跑同一测试集。

### 4.6 P3 已知限制

1. ~~端侧精度未在同一测试集上测量~~ → **ESPDET 416 与 MSRMNP 均已测（§4.7）**。
2. app 体积增加约 2.25 MB（esp-dl 运行库为主），6 MB 分区仍余 24%。
3. 冷启动首次推理 82 ms（MSRMNP，含模型加载）；ESPDET 416 首帧约 398 ms，
   后续 225–230 ms（见 §4.7）。

### 4.7 同一测试集框级精度（2026-11-07，ESPDET PICO 416 INT8）

测试集：`tools/vision/data/wider_subset` 的 40 正 + 10 负，经 SD 卡批量入口
（`CONFIG_SMART_HOME_FACE_BATCH_STANDALONE=y`，硬件 JPEG 解码 → RGB565 → 检测）。
匹配规则与 PC 基线一致：按分数贪心匹配，IoU ≥ 0.5 记 TP；未匹配但与 `faces_all`
（被 40 px 规则过滤的小脸）IoU ≥ 0.3 记 ignored；负样本任何框记 FP。

| 运行 | 分数阈值 / NMS | TP / FP / FN / ignored | precision / recall / F1 | 负样本 FP | 单帧耗时 |
|---|---|---|---|---|---|
| P4 ESPDET 416 INT8 | 0.3 / 0.7 | 74 / 13 / 7 / 63 | **0.851 / 0.914 / 0.881** | 0 | 225–230 ms |
| P4 ESPDET 416 INT8（离线过滤） | 0.6 / 0.7 | 70 / 5 / 11 / 41 | **0.933 / 0.864 / 0.897** | 0 | 同上 |
| P4 MSRMNP_S8_V1 INT8 | 0.3 / 0.3 | 17 / 0 / 64 / 1 | **1.000 / 0.210 / 0.347** | 0 | avg 20.6 ms（排除首帧），min 17.9，max 73.8 |
| PC YuNet FP32 | 0.6 / 0.3 | 77 / 18 / 4 / 119 | 0.811 / 0.951 / 0.875 | 0 | 3.62 ms |
| PC YuNet FP32 | 0.3 / 0.3 | 78 / 143 / 4 / 185 | 0.348 / 0.951 / 0.510 | 1 | 3.34 ms |

口径说明：

- 两端**不是同一个网络**（ESPDET 单阶段 INT8 / MSRMNP 两阶段 INT8 vs YuNet 单阶段

- **NMS 不同**：P4 ESPDet 用 0.7，P4 MSRMNP 与 PC 基线用 0.3；FP/ignored 不宜逐项

- 复现：`python tools/vision/bench_p4_log.py <serial.log> [--score 0.6]`。

> 说明：50/50 张图解码成功；负样本 10 张在两种模型下均 **0 误检**。
> ESPDet 416 @0.3 漏检 7 张脸（6 张图），唯一整图未检出的是
> `22--Picnic/22_Picnic_Picnic_22_541.jpg`；MSRMNP @0.3 漏检 64 张脸（34 张图），

## 5. 验收 3/4/5/6 · P4 事件驱动

### 5.1 状态机

```
主循环每 50 ms 读一次 PROTO_DEV_HUMAN 影子
  0 → 1 上升沿（且不在忙/冷却）→ 通知 vision_evt 任务
      ├─ 全屏预览滑入（320 ms ease-out）
      ├─ 抓 3 帧 → MSR+MNP 检测（角标先显示 CAM ON / SCAN）
      ├─ 角标显示 FACE n / 分数 或 NO FACE / CAM ERR
      ├─ 保持 5 s（期间画面实时刷新）
      └─ 滑出（260 ms）→ 图像还给主屏原位，冷却 30 s
```

阈值沿用 P3 的 0.3/0.3；检测在独立任务（12 KB 栈）里跑，不阻塞主循环的协议轮询。

### 5.2 交互实现

| 项 | 做法 |
|---|---|
| 平时 | 预览图隐藏、预览停止；待机层不叠任何预览块 |
| 事件时 | 临时启动预览；**PPA（硬件 SRM）把 800×640 中间的 800×470 裁切区缩放到 1024×600**，LVGL 按 1:1 整屏贴图，全程无软件缩放 |
| 动画 | `lv_anim` 改容器 y：入 320 ms `ease_out`，出 260 ms `ease_in`；动画期间**暂停预览刷新**，避免整屏重绘拖住动画 |
| 角标 | 左上角 (16,14) 的 ASCII 文本，Montserrat 24，`FACE 1  0.56` / `NO FACE` / `CAM ERR`；`lv_obj_move_foreground` 保证不被画面盖住 |
| 线程 | UI 操作全部经 `esp_lv_adapter_lock` + `lv_async_call` 切到 LVGL 任务 |

> 2026-11-02 修正记录：
> 1. 首版用软件把 800×640 缩放到 1024×600（每帧重采样 61 万像素），实测“巨卡”，且预览图长期挂在主屏导致待机层重叠；
> 2. 第二版改为 1:1 居中 + 平时隐藏/停预览，仍偏卡，且角标被画面覆盖（图像晚于角标挂入覆盖层）；
> 3. 当前版改由 **PPA 硬件缩放**输出 1024×600、角标提到最前、动画与刷新解耦。

### 5.3 实测（2026-11-02 现场）

| 项 | 值 |
|---|---|
| 触发 → 覆盖层出现 | ~8 ms |
| 触发 → 角标出结果（3 帧） | **~350 ms**（首帧预热 33 ms 量级） |
| 单帧检测（事件内） | 26.0 ~ 39.1 ms（首帧 42 ms 量级） |
| 有人脸 | 3/3 帧检出，`best 0.90 / 0.99 / 1.00` → 角标 `FACE 1  1.00` |
| 无人 | `NO FACE`（3/3 帧） |
| **预览帧率（PPA 全屏）** | **15 fps**；单帧刷新（PPA + cache 失效）**20.4 ms**，其余 ~45 ms 为 LVGL 整屏绘制 + DSI flush |
| 冷却/忙时重复触发 | 记录 `ignored (busy)` / `ignored (cooldown …)`，不重复执行 |
| panic | 无（连续多轮事件） |
| cache 对齐错误 | 修正前抓帧每次 3 条 `esp_cache_msync ... not aligned`；改为 128B 对齐后 **0 条** |

> 15 fps 的瓶颈不在 PPA（20.4 ms），而在 LVGL 软件渲染整屏 1024×600（~45 ms/帧）。
> 若需更高帧率，可选：① 预览降到 800×480 居中（约 22~24 fps，非全屏）；
> ② 只显示检测时的静态帧（不实时刷新）；③ 维持 15 fps 全屏。当前取 ③。

### 5.4 未验证项（如实标注）

1. **真实 PIR 触发（已验证 2026-11-03 现场）**：F103 的 `PROTO_DEV_HUMAN` 上升沿
   已实测触发完整链路（`PIR edge → vision event → 3 帧检测`）；Kconfig 自检开关
   `SMART_HOME_VISION_EVENT_SELFTEST` 保持关闭，触发源只应是 F103 的 PIR。
   本次实测：3/3 帧检出，`best 0.53 / 0.89 / 0.91`，随后规则 `fired=1` 开 RELAY1，
   离开 10 s 后 `Leave light` 关 RELAY1（ACK `state=1/0` 均核对）。
   **负向对照已完成（2026-11-07）**：PIR 边沿后 3/3 帧 `NO FACE`，随后无
   `RULES: fired`、无 `ACTUATOR_CMD dev=0x01`，灯保持关闭。
2. **规则联动的人脸确认开灯（已完成正/负向现场复核 2026-11-07）**：`Arrive light`
   的条件已由 `HUMAN>=1` 改为 P4 本地伪传感器 `FACE>=1`（`PROTO_DEV_FACE=0x19`，
   不走 UART 上行、F103 无此 ID）：PIR 边沿唤醒视觉事件 → 3 帧检测 →
   **检出人脸才置 FACE=1** → 规则下发 RELAY1 ON；`NO FACE`/坏帧置 0，不开灯。
   正向：`FACE 3/3 → fired=1 → RELAY1 ON`；负向：`NO FACE 3/3 → 无 fired、灯不亮`。
   `Leave light`（HUMAN<1，F103 侧 10s 保持）与 Arrive 由 UI「回家」卡片成对启停
   （rule id 1/2），既有的单开 Arrive 持久化配置会在启动时自动补齐 Leave。
3. **热拔插（验收 5，通过 2026-11-07 headless 复测）**：
   - 首次正常固件测试失败：插回后 `ISP: data type error` 刷屏 →
     `Interrupt wdt timeout on CPU0` panic。
   - 修复：capture 超时置 `camera_lost`，下一次预览前 `camera_deinit() → 200 ms
     → camera_init()` 重建 CSI/ISP；首次 capture 失败即中止扫描；预览启动失败
     返回 `CAM ERR`。
   - headless 复测（低功耗模式，PC USB 供电）：拔线 → `capture timeout` →
     `CAM ERR`，**无 panic**，链路保持 UP；插回后再触发 →
     `Camera marked lost — reinitializing before preview` →
     `Camera init complete` → `[OK] Camera recovered after hot-plug` →
     3/3 帧 `FACE 1 0.89`。全程无 brownout、无重启。

### 5.5 功耗口径（验收 4）

本板**没有摄像头电源开关**，OV5647 在 `camera_init` 时开流后一直工作；停/开预览只
影响 CSI/DMA 与 LVGL 渲染，省不了模组本身功耗。因此本阶段无法给出“常开 vs 事件触发”
的电流对比，仍沿用阶段六口径：**无仪器不写数字**，只保留测量方法。

### 5.6 隐私（验收 6）

- 帧只在 PSRAM：检测任务复用同一块 1,024,000 B 缓冲，事件结束不释放也不落盘；
- 不上行：网络侧只发设备状态，无图像字节；
- 工作指示：本板无可控 LED，用左上角 `CAM ON` 角标替代（与 docs/01 的偏差已在计划中记录）。

## 6. 已知限制

1. **ISP 白平衡不可用**（rev<3.0）。当前依赖 Bayer 相位修正 + 环境光，色彩为传感器原始响应；
   如需更好肤色，可在后续做软件白平衡（本次实测非必需）。
2. **低照度噪点明显**：AEC 增益上限 15×、曝光上限 984 行（50fps 模式）。方案
   a) 降帧率换取更长曝光；b) 软件时域/空域降噪；c) 补光。按计划留到 P2/P3 评估。
3. 未测：JPEG 质量 60/90 的对比、硬件解码耗时、连续编码发热/功耗。
4. 未测：摄像头热拔插鲁棒性（计划的 P4 项）。
