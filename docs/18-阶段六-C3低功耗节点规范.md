# 阶段六 · ESP32-C3 低功耗无线节点规范

> 版本 v0.1 ｜ 2026-10-24 ｜ 状态：**可行性验证已完成，待评审后进入实现**
> 前置：阶段二（协议帧）、阶段五（MQTT/HA）已验收；`docs/17` 为本文上行链路依据。

---

## 1. 范围

C3 作为**无屏电池节点**接入现有系统，承担三件事：

1. **BLE 配网**：手机 App 写 Wi-Fi 凭据，节点存 NVS 后自行连网；
2. **传感器上行**：C3 采集的数据经 MQTT 进入 broker / HA，复用阶段五链路；
3. **BLE 本地控制**：手机就近连接即可读写节点状态（不依赖路由器和 broker）。

**不做**：P4 侧的 BLE 主机能力。P4 的射频由板载 C6 经 esp_hosted 提供（ADR-008/012），
启用 BLE 主机需重烧协处理器固件，风险见 ADR-024。

## 3. 可行性验证结论（2026-10-24，全部实测）

### 3.1 硬件缺陷：板载天线严重失配

参考社区实测（[smzdm 文章](https://post.smzdm.com/p/ak8d8mm9/)，引 B 站“微联编程”两条视频）：
该板 2.4GHz **驻波比 5.81**，约一半发射功率被反射，**接收正常但发射极弱**。

与本项目观测完全吻合：

| 阶段 | 现象 |
|---|---|
| 降功率前 | 扫描 RSSI **-43dBm**、ch4、auth=3 均正常，但 `init→auth` 计时 **1002ms** 后报 `AUTH_EXPIRE`，AP 收不到认证帧 |
| 排除项 | 密码逐字符一致、SSID 正确、关掉 BLE 后依旧失败、热点下无其它设备占满 |
| 修复后 | `esp_wifi_set_max_tx_power(34)`（8.5dBm）→ `auth` 33ms、`assoc`、`connected`、`got ip 10.48.69.233` |

### 3.2 BLE GATT server（验证固件）

| 项 | 实测 |
|---|---|
| 广播 | 名称 `SHH-C3-TEST`（现为 `SHH-C3`），含服务 UUID `0xFFF0`（现同时广播 `0xFFF3`），间隔 20~30ms |
| 连接间隔 | 固件请求 24（30ms）；手机一度改 6（7.5ms），固件再次请求后回到 24 |
| Notify | `0xFFF1` 订阅后 1Hz 推送。验证固件为 4 字节原始载荷，**现改为阶段二完整帧（12 字节）**，见 §5 |
| 控制 | `0xFFF2` 写 `01` → LED 亮；写 `00` → 灭（日志 `write cmd=1 -> LED ON` + 目视确认） |
| 重连 | 远端断开（reason=531 / 0x13）后自动重广播并接受重新连接（conn 累计 3） |
| MTU | 固件 `ble_att_set_preferred_mtu(247)`；手机未发起交换时 `mtu=0`，12B 载荷走默认 23 可用 |

### 3.3 BLE + Wi-Fi + MQTT 共存

连续 880s（14.7 分钟）记录：`BLE conn=3 sub=1`、`WiFi disc=0`（RSSI -34~-41）、
`MQTT up=1` 且 broker 侧 1Hz 收到 `c3/test/link`、`nfail=0`、最小堆 105.8KB。

> 已超过原定 10 分钟共存指标。

### 3.4 Light-sleep 下的保持（验收 8）

必要条件（官方要求三条同时满足）：
`CONFIG_PM_ENABLE` + tickless idle + `esp_pm_configure(light_sleep_enable=true)`、
Wi-Fi `WIFI_PS_MIN_MODEM`、**BLE `CONFIG_BT_CTRL_MODEM_SLEEP=y`**（IDF 默认关闭，漏掉会导致
BLE 与 Wi-Fi 一起断流），BLE 低功耗时钟取主晶振（本板 32k 晶振不可用，见 §7-7）。

| 版本 | 采样 | 结果 |
|---|---|---|
| light sleep 开、BLE modem sleep 关 | 129s | 1 处 40s 断流（缺 40 条） |
| light sleep 开、BLE modem sleep 开（Main XTAL） | 111s | **0 中断**，seq 全程连续 |
| 同上，手机侧 | 2 分钟 | `0xFFF1` Notify **未断** |

> 结论：功能层通过。**是否真的进入 light sleep 带来的功耗下降，仍需电流表实测**（验收 4）。
>
> 补充证据（2026-10-30，串口 STAT 日志 `esp_pm_dump_locks`）：
> `light_sleep_counts: 454`、`light_sleep_reject_counts: 0`、模式统计 `SLEEP 44% / APB_MAX 45% / CPU_MAX 10%`，
> 且 `mpi_sleep`（NO_LIGHT_SLEEP 锁）Active=0 —— **系统确实在进入 light sleep**，
> 当时万用表读到的 30~60mA 属于欠采样假象，不能当稳态电流用。

## 4. 系统设计

### 4.1 角色划分

```
手机 App ──BLE──> C3 ──Wi-Fi/MQTT──> broker ──> P4 面板 / HA
                   └──BLE──> 手机（就近控制，不经路由器）
```

C3 与 P4 之间**没有直连链路**，全部经 MQTT 收敛，理由见 ADR-024。

### 4.2 BLE 服务定义（生产版）

在验证固件基础上扩展，仍用 16 位自定义 UUID：

| 服务 | 特征 | 属性 | 用途 |
|---|---|---|---|
| `0xFFF0` 主服务 | `0xFFF1` | Read + Notify | 遥测：阶段二帧格式的 payload（§5） |
| | `0xFFF2` | Write | 控制：`01`/`00` 开关；沿用验证固件语义 |
| `0xFFF3` 配网 | `0xFFF4` | Write | 文本 `ssid=xxx` 或 `pass=xxx`（不用 HEX，手机端 TEXT 模式即可） |
| | `0xFFF5` | Write | 提交配网（写 `1`），触发连接 |
| | `0xFFF6` | Read + Notify | 配网状态：`0` idle / `1` connecting / `2` connected / `3` failed(+reason) |

**安全**：配网服务要求**加密链路**（LE Secure Connections + bonding，Just Works），
未加密时写请求返回 `BLE_ATT_ERR_INSUFFICIENT_AUTHEN`；遥测/控制可匿名访问。
`ble_store_config_init()` 已在验证固件中保留，bonding 信息可持久化。

### 4.3 配网流程

1. 上电且 NVS 无凭据 → 只广播（名称 `SHH-C3`）；
2. App 依次写 `0xFFF4`（`ssid=...` / `pass=...`）、写 `0xFFF5=1`；
3. 节点落 NVS → 连 Wi-Fi，`0xFFF6` 推送状态；
4. 成功则记录 RSSI 并开始上行；失败则在 30s 内重试 3 次后回到广播态，状态里带 `reason`。

### 4.4 上行（MQTT）

沿用 `docs/17` 命名：`base = smart_home/<node_id>`，本节点 `node_id = c3node`。

| Topic | 方向 | QoS/Retain | 内容 |
|---|---|---|---|
| `homeassistant/<component>/c3node/<obj_id>/config` | 发布 | 1 / ✔ | HA 自动发现 |
| `smart_home/c3node/availability` | 发布 | 1 / ✔ | LWT `offline` |
| `smart_home/c3node/state/<obj_id>` | 发布 | 1 / ✔ | 传感器状态 |
| `smart_home/c3node/cmd/<obj_id>` | 订阅 | 1 / — | 云端控制 |

`node_id` 用 Kconfig 默认 + NVS 覆盖，与 P4 的 `mqtt_node` 机制一致。

### 4.5 低功耗策略

| 模式 | 用途 | 实现状态 | 电流 |
|---|---|---|---|
| Active | 配网 / 高频采样窗口 | 需把 `wifi_tune()` 的 PS 改为 `WIFI_PS_NONE`（未做） | 未实测 |
| Modem-sleep | 常规联网上报（BLE 关闭） | 已具备（`C3_BLE_ENABLE=n` + `C3_PM_LIGHT_SLEEP=n`） | 未实测 |
| Light-sleep | 连接保持 + 低频上报 | 已具备（ADR-026 三项配置齐全） | **未实测**（仅功能层验证） |
| Deep-sleep | 长周期节点（RTC 定时唤醒） | **未实现**（`app_main` 无 `esp_deep_sleep_start` 入口） | 未实测 |

> **2026-10-30 决定：功耗实测（验收 4）推迟。** 手上只有万用表 mA 档直串，采样 1~2 次/秒，
> 对「毫秒级发射尖峰 + 大部分时间低电流」的波形严重欠采样；实测读数在 30~60mA 之间跳动，
> 无法换算成可信的日均电流。Deep-sleep 也还没有代码入口。
> 具备积分式电流表（或分流电阻 + 数据记录仪）后再补测。**在此之前不对外给任何功耗/续航数字。**

占空比由「上报周期」与「BLE 连接保持需求」共同决定；日均电流与续航推算待实测后再给。

## 5. 协议复用（阶段二帧格式）

**复用**：载荷内部沿用 `docs/03` 的 `SOF(AA55) + VER + TYPE + SEQ + LEN + PAYLOAD + CRC16`，
设备类型号与 `PROTO_DEV_*` 共用；JSON 只在 MQTT 侧做封装（与阶段五一致）。

**差异**（必须写清楚，否则会被问倒）：

| 维度 | 阶段二（UART） | C3（BLE / MQTT） |
|---|---|---|
| 物理层 | UART 115200 8N1 | BLE GATT Notify / TCP |
| 帧同步 | 需要 `0xAA55` 扫描重同步 | BLE 有包边界，SOF 可省略或保留做版本识别 |
| 可靠性 | 应用层 ACK + 重传 + TTL | BLE 链路层重传；MQTT QoS1 提供一次投递 |
| 分片 | `LEN ≤ 256`，一次一帧 | MTU 23~247，超长需在应用层分片 |
| 校验 | CRC16 必选 | 保留 CRC16（跨链路一致性 + 端到端检错） |

**实现**（`firmware/c3-node/main/frame.c`）：`frame_crc16()` 与 `frame_build()` 是**唯一**的 CRC/组帧实现，
BLE Notify 与 MQTT 上行都用它产出的同一份字节（`ble_svc_notify_frame()` 与 `net_link_publish()` 接收同一 buffer）。

- BLE `0xFFF1`：Notify 值 = 完整帧（10~12 字节）
- MQTT：JSON 保留可读字段，并附 `"frame"` 十六进制，同一份帧字节
- 上电自检：`frame_selftest()` 断言 `CRC16("123456789") == 0x29B1`，日志 `frame crc selftest PASS`

实测样例（broker 抓到，并用独立脚本按同一算法复算）：
```
{"seq":33,...,"frame":"aa55021021000200d901bdab"}
偏移:  aa55 | 02 | 10 | 21 00 | 02 00 | d9 01 | bd ab
含义:  SOF   VER  TYPE  SEQ=33  LEN=2   rssi/flags CRC=0xABBD（复算一致）
```
手机端 `0xFFF1` Read 值（2026-10-29）：`AA 55 02 10 XX XX 02 00 DX 03`
—— 与 MQTT 侧结构一致；末字节 `03` = bit0 MQTT 在线 | bit1 BLE 已连接。

### 5.2 跨链路 CRC / 帧格式一致性单测

三份实现是**独立代码**，必须逐字节对拍，不能只靠"看起来一样"：

| 实现 | 文件 | 算法 |
|---|---|---|
| C3 | `firmware/c3-node/main/frame.c` | 逐位法（0x1021 / 0xFFFF） |
| F103 | `firmware/f103-node/APP/comm/crc16.c` | 运行时建表（`crc16_init()`） |
| P4 | `firmware/p4-hub/components/protocol/crc16.c` | 常量表 |

测试在 PC 上跑（mingw gcc，不依赖 ESP-IDF，也不需要板子）：

```
powershell -ExecutionPolicy Bypass -File firmware\tests\crc_crosslink\run.ps1
```

6 组用例、**706 条断言全部通过**（2026-10-30 实测）：

1. 检查值 `CRC("123456789") == 0x29B1`（三份实现各查一次）；
2. 空缓冲 `== 0xFFFF`（初值边界）；
3. 随机向量三方一致，长度覆盖 0..256（257 组）；
4. C3 `frame_build` 与 F103 `proto_frame_build` **字节级一致**（6 种 TYPE × 7 种 LEN，含 0/1/255/256）；
5. C3 组帧 → F103 `proto_parser_feed()` 解析：type/seq/len/载荷/帧内 CRC 全部吻合；
6. 负向：载荷篡改 → `crc_errors=1` 且不投递；`LEN=257` → `len_errors=1`（不得写越载荷缓冲）；
   版本 `≠0x02` → `len_errors=1`；前导垃圾后仍能重同步收到帧。

> F103 与 P4 都导出 `crc16_compute`，测试编译时用 `-Dcrc16_compute=f103_crc16_compute`
> 对 F103 侧改名，`proto_frame.c` 同步改名，确保被解析器调用的是 F103 自己的实现（不串味）。

## 7. 已知限制与风险

1. **发射功率被限制在 8.5dBm**（ADR-025）：距离与穿墙能力明显弱于正常板。
   若节点需跨房间部署，必须改硬件（外置 FPC 天线）或换品牌板，不能靠调软件解决。
2. **同款板批次差异大**：本块可用不代表批量可用；批量采购前须抽测关联成功率和 RSSI。
3. **单 2.4G 射频分时**：BLE 与 Wi-Fi 共用天线，`CONFIG_ESP_COEX_SW_COEXIST_ENABLE=y` 必须保持；
   高吞吐场景（如 OTA）与 BLE 长连接并发时需复测。
4. **MTU 依赖手机端发起**：不同 App 行为不一致，协议不能假设 247 可用。
5. **无直连链路**：C3 与 P4 全部经 broker，broker 挂了本地仍可用 BLE，但面板不可见。
6. **首次连接常被中断**：连接后立即发起配对，实测手机会在服务发现阶段主动断开一次
   （`reason=531` / `enc change status=7 ENOTCONN`），第二次连接才稳定。属 Android 侧行为，
   暂按"重连一次即可"处理，量产前需复测多机型。
7. **32.768kHz 晶振不可用**：原理图有 `Y1 32.768kHz`，但即使把校准窗口拉到约 1 秒并强制
   `RTC_CLK_SRC_EXT_CRYS`，仍报 `32 kHz XTAL not found`、`src=0 hz=136000 xtal_en=0`。
   即实物未贴装/虚接/损坏，**不能把外部 32k 作为低功耗时钟**。
   现取 BLE 低功耗时钟 = 主晶振（40MHz），文档支持与 light sleep 共存，但比 32k 费电。
8. **light sleep 下 USB-Serial/JTAG 不可用**：串口日志与常规烧录都会失效，实测打开端口报
   `ERROR_GEN_FAILURE(31)`。烧录必须按住 BOOT 进 ROM 下载模式；调试改用外部 UART
   （CH340 → GPIO20/21，115200），或临时关闭 light sleep。
9. **掉线提示延迟与 keepalive 挂钩**：节点在热点/NAT 后，TCP 不会随断电立即断开，
   broker 要等 `1.5 × keepalive` 收不到 PINGREQ 才发 LWT。
   旧值 30s → 实测约 45s 才变 `offline`；**降到 12s 后实测 12s**
   （2026-10-30，broker 日志：最后一条上行 `...4116` → LWT `...4128`，中间无任何 C3 报文）。
   因此 P4 的 90s 无数据判定与 HA `expire_after` 仍以 LWT 为前置，**不能宣传"秒级掉线检测"**。
10. **TLS 用自签 CA**：设备只信任仓库内 `certs/ca.pem`（打进了 mbedtls custom bundle，ADR-027）。
    换热点 IP 后必须重签服务器证书（`tools/gen_mqtt_certs.py --ip <新IP>`，脚本会复用原 CA），
    否则设备侧 hostname 校验失败、直接连不上；设备端无需重烧。
