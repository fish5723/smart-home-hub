## 一、硬冲突（文档 ↔ 代码直接矛盾）

1. **协议引脚表（docs/03 §5.1）**：文档引脚（PB12/PB13/PB14/PB9 一组）与实际全部不符。
   实际（[bsp_pins.h](file:///e:/workspace/smart-home-hub/firmware/f103-node/BSP/bsp_pins.h) 单点维护）：RELAY1=PB14（低吸合）、RELAY2/水泵=PB15（高启动）、LOCK=PB8、BEEPER=PB12、PIR=PB13（EXTI）；设备号 RELAY1=0x01、RELAY2=0x02、LOCK=0x03、BEEPER=0x04。
2. **数值编码（docs/03 §4）**：文档称 int32 定点、禁用 float；实际 SENSOR_REPORT 条目 6B = dev_id(1)+qual(1)+**float32(4)**（两侧 app_proto.c 同构：f103 `:145`、p4 `:240`）。
3. **esp_hosted 版本（ADR-012、docs/07:36）**：ADR-012 标题即「锁定 2.9.6 禁止升级」；实际 dependencies.lock = **3.0.9**（esp_wifi_remote 1.6.5），且 idf_component.yml 写的是 `>=2.11` / `>=1.6.5` 范围、并未锁定（docs/07:36 却已勾选「锁定版本」）。3.0.9 的旧配置符号已更名，全新生成 sdkconfig 会配错。
4. **ACK 超时（docs/03 正文、docs/06:99）**：文档写 50ms；实际 `ACK_TIMEOUT=100ms`（protocol.h，两侧同源）。docs/12 决策 4 已声明「别照抄 50ms」，但 docs/03 与面试映射仍未改。

## 六、ALARM_EVENT 实现口径（B5 落地，2026-10-18）

此前"文档有描述、代码无生产者"；本轮补齐生产者与消费者。

| 字段 | 长度 | 说明 |
|---|---|---|
| `alarm_id` | 1B | `PROTO_ALARM_*`：0x01 可燃气(MQ-4) / 0x02 空气质量(MQ-135) / 0x03 水泵干烧 / 0x04 锁动作失败 / 0x05 传感器故障 / 0x06 链路中断 / 0x07 存储失败 |
| `level` | 1B | 0=提示 1=警告 2=紧急（`PROTO_LEVEL_*`） |
| `value` | 4B | 触发值，**float32**（与 SENSOR_REPORT 同口径；文档原写 int32 定点，一并修正） |
| `threshold` | 4B | 阈值，float32 |

- **生产者（F103，`app_beep.c`）**：MQ-4/MQ-135 百分比 ≥60% 且 `quality==VALID`（与本地蜂鸣判定完全一致）→ **上升沿立即上报**，之后每 30s 节流重发；TX 槽被占（1Hz SENSOR_REPORT 在途）时挂起，`AppProto_Poll` 每轮重试（`app_proto.c` 的 `AppProto_NotifyAlarm` / `alarm_retry_poll`）。
- **消费者（P4，`app_proto.c`）**：解析进 `alarm_shadow_t` → `ESP_LOGW` 打印 → 回 `ALARM_EVENT_ACK`；**解除由数据判定** —— 收到对应设备（0x01→`PROTO_DEV_MQ4`、0x02→`PROTO_DEV_MQ135`）的新鲜有效数据且低于阈值时自动清 `active`。
- **安全语义不变**：本地蜂鸣/关断等动作全部在 F103 完成，本帧只用于"通知面板显示"（ADR-009 故障域隔离）。
- **UI 呈现**：`AppProto_GetActiveAlarm()` 已就绪；面板/告警详情卡片的接线上屏列入「阶段四补完」。

### 7.6 待机壁纸帧率：圆角裁剪导致 PPA 失效（2026-10-19，用户拍板「直角」）

**现象**：待机动态壁纸实测只有 14fps（目标 30）。加分段打点后定位到成本全在绘制段：
`prep≈110us`、`draw≈48ms`、`flush≈80us`。`flush` 近零，说明「提交 + 等面板帧缓冲切换」
**不是**瓶颈（此前怀疑过，已被数据否定）；`sink≈30ms` 只是 LVGL 在 48ms 绘制期间持续
持锁、播放器随机到达的必然结果。

**根因**：`s_card` / `s_video` 开了 `clip_corner`（圆角裁剪）。LVGL 一旦开启圆角裁剪，
就为子对象单独建 ARGB8888 图层并生成圆角 mask（`lv_refr.c` L162-L190）；壁纸每帧
整块失效 → 每帧建层 + 生成 mask。适配器的 PPA 路径两条都踩：明确
"PPA doesn't support complex masking"，且要求目标图层必须是 RGB565
（`lvgl_ppa_accel_v9.c` L356-L363）→ 整块退回 CPU 软件混合。

**四次实测对照**（同一台 P4 / JD9165BA）：

| 配置 | `draw` | `dispfps` | `drop`（每 5s） |
|---|---|---|---|
| `DOUBLE_FULL` + 圆角裁剪 | — | 14 | 72 |
| `DOUBLE_DIRECT` + 圆角裁剪 | 48ms | 17 | 44 |
| `DOUBLE_DIRECT` + 只关 `clip_corner`、保留 radius、另叠 4 张静态角片 | 14~34ms | 20 | 50 |
| `DOUBLE_DIRECT` + `radius`/`clip_corner` 全部归零 | **13ms** | **30** | **3** |

**最终实现**：`s_card` / `s_video` 的 `radius` 与 `clip_corner` 一并归零，接受直角。
中途试过的「保留 radius + 一次性生成的静态角片」方案已放弃（实测仅到 20fps）。

**与原型的一致性**：视频窗口 / 媒体卡取**直角**；原型（`ui/prototype/stage4-ui.html`）已在
2026-10-19 收尾时同步为 `border-radius:0`，三端一致（`docs/15` 有意偏差 #4 随之收敛为"已同步"）。
**但技术禁令不变**：若将来要恢复圆角，必须让圆角**不参与每帧重绘**（例如把圆角直接烤进 JWP 帧像素），
**不要改回 `clip_corner`** —— 理由已锁在 `standby_ui.c` 文件头注释与原型 CSS 注释里。

**保留的诊断能力**：`SMART_HOME_STANDBY_SELFTEST` 每 5s 打印的三段 `prep` / `draw` / `flush`
由本次排查引入，用于日后帧率问题快速归因（用法见 `firmware/p4-hub/main/README.md` §4）。

### 7.8 拨规则开关时「亮蓝一瞬」（2026-10-19，**未定因，进行中**）

**现象**：在自动化页反复拨 3 个规则开关时，屏幕闪一下**亮蓝**（一帧左右），随后恢复正常；
不伴随重启、串口无新 `W`/`E`。**语言开关（设置页）不闪。**

**已排除**（有实测或代码依据，不要重复走）：

| 候选 | 否证方式 |
|---|---|
| `DOUBLE_DIRECT` 局部刷新露出陈旧帧缓冲像素 | 改回 `DOUBLE_FULL`（每帧整屏重绘）做 A/B：**依旧闪**。该现象与刷新模式无关 |
| 刷成整屏重绘就能顺带解决 | 同一 A/B 实测：FULL 下 `draw` 31.5ms / `dispfps` 20，比 DIRECT 的 13.4ms / 30 更差，故已改回 DIRECT |
| 某处用了"页面底色" `TK_COLOR_BACKGROUND=0x0F172A` | 该 token **定义了但全工程从未使用** |
| 待机层 `s_visible` 与 `s_cover` 不同步（SELFTEST `vis=1` 引起怀疑） | `standby_ui_show()/hide()` 两处都同时改 `s_visible` 与 `LV_OBJ_FLAG_HIDDEN`，无不一致 |
| UI 调色板里有亮蓝 | 调色板（INK/ALT/HAIR/SURFACE/METAL/CREAM）全是暗色与米白，唯一强调色是红 `DANGER=0xEF4444`。亮蓝只可能来自：待机层晴天兜底渐变 `0x2E6FB7→0x9CC8E8`（`standby_ui.c` L172），或 LVGL 默认主题主色 `0x2196F3` |
| 「亮蓝」来自待机层视频区（被画出一帧） | **洋红测试**：把该处兜底渐变与 `s_video` 初始底色临时改成 `0xFF00FF` 后，用户实测**闪的颜色不变（仍是亮蓝）** → 与待机层无关。诊断标记已还原 |
| 闪烁范围是某个控件/区域 | 用户实测：**整屏、仅一帧、极快** → 更像面板/总线层事件，而非某个控件被画出来 |

**四组对照结果（2026-10-19 用户实测）**：

| 操作 | 写 NVS | 重绘规模 | 是否闪 |
|---|---|---|---|
| 设备页拨开关（只发指令，不写 NVS） | ❌ | 小（行 + toast） | ❌ |
| 设置页语言开关 | ✅ 小值 | **大**（`apply_lang()` 重设大量文案） | ❌ |
| 设置页待机超时 30→60s | ✅ 小值 | 小（一个标签） | ✅ |
| 自动化页规则开关 | ✅ 792B blob | 小（行 + toast） | ✅ |

结论：
1. **"写 NVS"与"闪"强相关** —— 不写 NVS 的设备页开关不闪；写 NVS 的两组闪。语言开关虽然也写 NVS，
   但紧接着**大面积重绘把那一帧盖掉**，所以看不见（这正是它成为例外的原因）。
2. **待机超时也闪 → 与发指令/UART 无关**（该项不下发指令）。
3. 用户实测「**均匀纯色 + 整屏 + 仅一帧**」→ 属**面板/总线层**事件，**"LVGL 主题蓝控件"分支排除**。

**根因（2026-10-19 已证实）**：**NVS 落盘本身**触发的面板一帧异常。
证实方式：把规则集与「待机超时」两处的 NVS 落盘临时跳过（只改 RAM）→ 用户实测**两处都不再闪**；
恢复落盘后重现。机制：`nvs_set_*` + `nvs_commit()` 期间的 flash 操作占用 MSPI，而 DSI 正按行
从 PSRAM 拉帧缓冲 → 断流一帧，面板输出默认色（均匀亮蓝）。
⚠️ 这是**总线层面的物理争用**，与在哪个任务调用无关 —— 所以"把写入挪到独立任务"**不能修**。

**修复（降频，已落地）**：规则集改为**延迟合并落盘**（`NVS_DEBOUNCE_MS = 1500`，在已有的
`rule_runtime_tick()` 里落盘）—— 连拨 N 次只写 1 次：闪烁从「每次拨都闪」降为「停手后闪一下」，
同时大幅减少 flash 擦写次数。语义代价：改动后 1.5s 内掉电会丢这次改动；
`rule_runtime_set_enabled()` 不再同步返回落盘结果（失败只记日志，UI 的「保存失败」提示因此不再触发）。

**残留（未修）**：其它同步落盘点（如设置页「待机超时」的 `storage_set_u32`）仍是**每改一次闪一帧**；
语言开关因随后**大面积重绘把那一帧盖掉**所以看不见。

**归因手段（保留）**：`save_set()` 在 `SMART_HOME_STANDBY_SELFTEST=y` 时打印
`save_set #N slot=? ?us blob=?B`（合并后每次落盘打一条）。

**两处需要记录的实现取舍**（非文档差异，是新增事实）：
1. **IDF 6.1 无内置 esp-mqtt** → 必须用 registry 组件（见 §4.5 注）。
2. **云命令不在 MQTT 事件任务里直接下发**：协议层 `ProtoTx` 是单发送槽、无锁；
   云命令经 `mqtt_service` 内部队列投递、由 `app_main` 主循环在 `AppProto_Poll()` 后统一
   调用 `AppProto_SendActuatorCmdEx(..., CLOUD)`，把这条**新增**写路径收敛到主任务上下文。
   （UI/规则引擎原有直接调用路径未改动。）
3. **`expire_after=60` + 每 20s 强制重发**：用于在 P4↔F103 链路断或 `quality != VALID` 时
   让 HA 如实显示 `unavailable`，不粉饰「在线但无数据」。
