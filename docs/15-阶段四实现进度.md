## 端到端延迟打点（2026-10-14）

验收要求"屏幕点击 → 继电器吸合 < 200ms"，本轮植入可测量的打点：

- **起点**：UI 点击事件调用 `AppProto_MarkUiClick()`（`esp_timer`），见 `ui_pages.c` 的 `dev_cb` / `modal_ok`。
- **终点**：P4 收到 F103 的 `ACTUATOR_CMD_ACK` —— 此时 F103 已写完 GPIO 并回 ACK。
- **F103 侧耗时**：`app_proto.c` 的 `PROTO_ACTUATOR_CMD` 分支用 `delay_micros()`（DWT）测"收帧 → 写 GPIO"，填入 ACK `payload[3..6]`（微秒，little-endian）；P4 解析后一并打印，用于拆分耗时。
- **只能区间差**：两芯片时钟各以自身复位为基准，跨芯片绝对时间不可比，故只回传"区间耗时"。

P4 串口日志格式：

```text
LATENCY  dev=0x01  click->relay=3.12 ms  f103_proc=0.21 ms  min=2.98 max=3.40 avg=3.12 ms  n=8  over200=0
```

测量步骤：

1. 烧录两端固件，确认 P4 串口出现 `HELLO_RSP`、`LATENCY` 前缀可用。
2. 在设备页反复点 RELAY1/RELAY2 开关 10 次以上（每次间隔 >1s）。
3. 取 `LATENCY` 行的 `max` 与 `avg` 作为验收数据；`over200` 必须为 0。

边界说明：

- P4 往返含**回程 UART**，是略保守的上界；真机 `<200ms` 判定以本日志为准 —— **但本轮仅完成打点，尚无实测数字，结论一律标"待实测"**。
- 规则引擎触发的命令不调用 `MarkUiClick`，不计入该统计（符合 ADR-022"只算 UI 点击→命令通道"）。
- `LATENCY no ACK within 1s` / `cmd dropped (tx busy)` 表示该次点击未形成有效样本，重测即可。

### 实机测试反馈后的修正（2026-10-18）

用户首次上板测试后报回的问题，其中两条是**真 bug**：

1. **告警不恢复（单位不一致）**——F103 的 `SENSOR_REPORT` 对 MQ-4/MQ-135 上报的是 `gas_ppm`/`air_ppm`（**ppm 量级**），而 `ALARM_EVENT` 的 `value`/`threshold` 是**百分比**（阈值 60%）。P4 侧"收到新鲜有效数据即解除告警"是拿该 ppm 值去比 60 → 恒不成立 → **告警一旦触发就永远解除不掉**。已改为上报 `d->gas`/`d->air`（0~100 百分比），与面板 0~100 阶梯和 60% 阈值同单位；顺带修正了屏上 `%.0f%%` 显示 ppm 的失真。
2. **面板读了未初始化的告警影子**——`AppProto_GetActiveAlarm()` 在"未告警"时**不写** `out`，UI 直接读会拿到未初始化值（"已恢复"态因此不可靠）。新增 `AppProto_GetAlarmShadow()` 无条件拷贝最近事件；「已恢复」只在事件后 10 分钟内显示，之后自动回到「无告警」。

其余按用户要求调整：

3. **待机层**：去掉天气条件文本（不再显示"阴/多云"），页脚只留**图标 + 温度**；图标改 40px 配 48px 数字、整组右对齐（右缘 924）。
4. **WiFi 列表**：由固定 4 行改为**可上下滑动的容器**（行池 = `WIFI_SCAN_MAX_AP`，`LV_SCROLLBAR_MODE_AUTO` 自动出滚动条），结果多于可见高度时可滑动浏览。
5. **断链时的规则开关**：规则行新增「**已暂停**」状态词（链路离线时显示，开关位置仍反映持久化的用户意图），点击弹「已保存 · 链路恢复后生效」——避免"能打开却没效果"被误判为故障。

并按 F103 侧日志修掉一处**上电假告警**：

6. **`[APP] *** CRASH in: ? ***` 是假告警**——`g_sched_trace` 在 `.noinit` 区，复位后可能是随机值；更实际的原因是 `SCHED_TRACE_IDLE`(99) **本来就不在名字表里**，所以"真正卡在主循环体"的崩溃也只会打印成 `?`。已改为：只认表里存在的 ID，其余（越界/随机）一律当"无记录"不打印，并把 IDLE 补进表（用 22 项小表 + IDLE 单列，避免 100 项稀疏数组多吃 ~1.5 KB Flash）。F103 重编译后 FLASH 47244 B / 64 KB = 72.09%。

补充一条 MQ 的**预期行为**（不是 bug）：重标定需要约 **140 s**（预热 60s + 老化 60s + R0 采样 20 次）才进 READY，期间 MQ 一直是 `[INVALID]`。已排除两种怀疑：`power_on_ms` 是 `uint32_t` 不会溢出；占位分压比**不会**降级质量（质量只由 `state != MQ_CALIB_READY` 决定）。实测确已 READY：`MQ-4 160mV Rs/R0=3.47 200ppm [OK]`、`MQ135 1095mV Rs/R0=1.21 100ppm [OK]`。

更正上一版的"三条硬件侧事实"结论：SOIL/RAIN/DHT11 曾在上电初期全部 INVALID，**数分钟后自行恢复 OK**（同机实测 T=31.0°C/H=51%、SOIL 14~17%、RAIN 96~98%）——属上电初期未稳定，**不是持续故障**；其中 RAIN 的"下雨"是用户把探头放入水杯的**有意测试**，反而证明该通道正常。仍需处理的硬件项只剩一个：MQ 的 `divider_ratio` 仍是占位值 1.0，需实测后填入 `app_mq_calib.h`；在此之前 ppm 与百分比**不可信**（只能当"过没过阈值"用）。

**MQ 百分比量程已统一（用户拍板「统一量程」）**：原实现可燃气用 `ppm*100/5000`、空气质量用 `ppm*100/1000`，却共用同一个 60% 告警阈值 —— 屏上「优/良/中/差」阶梯对两者意味着不同的 ppm。现统一到 `MQ_PCT_FULL_SCALE_PPM = 1000`（单一出口常量定义在 `app_mq_calib.h`，`app_mq4.c` / `app_air.c` 都引用它）：同一个百分比在两条通道上代表同一个 ppm，阶梯与 60% 阈值含义一致。

选 1000 而不是 5000 的理由：MQ-135 的曲线端点是 100~1000 ppm，取 5000 会让空气质量**永远到不了 60%**（阶梯恒「优」、告警恒不触发）；1000 是两条曲线都能真实覆盖的最大上限。**代价**：可燃气告警点随之降到 600 ppm ≈ 1.2% LEL，偏保守；若实机误报，单独上调 `app_beep.c` 的 `BEEP_GAS_ALARM_PERCENT`（该阈值本就独立于量程）。


实机已确认通过的部分：六个 BinFont 全部加载（未知 SSID 缺字形属预期）、执行器回读、语言开关、两张下级界面、`LATENCY ... over200=0`。
