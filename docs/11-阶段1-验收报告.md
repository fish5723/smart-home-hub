| 配置 | 整改前 | 整改后 | 变化 |

| Debug | 61,272 B（93.49%） | **39,492 B（60.26%）** | −21,780 B |

**两处改动带来这个结果：**

1. **移除浮点 printf（`-u _printf_float`）**。工程里只有约 15 处用 `%f`，却把 newlib 整套浮点格式化拉进固件（`_dtoa_r` 2,984 B + `_printf_float` 1,112 B + `_printf_i` 572 B ≈ 4.7 KB）。已全部改用新增的 `common/fmt_fixed.h` 定点格式化。**浮点运算不受影响**（软浮点仍在），只是不再用浮点格式化；已验证 `_dtoa_r` / `_printf_float` 从符号表中消失。
   - 顺带修掉一个观感 bug：`app_dht11.c` 原用 `%.1f` 打印，但驱动只填整数部分，所以永远显示 `.0`——看起来像"精度正常"，其实根本没有小数位。
2. **Debug 优化等级 `-O0` → `-Og`**。这是体积下降的主要来源。原因：`-O0` 下 Debug 已达 93.49%，阶段 2 的协议栈（约 5KB）会把 Debug 撑爆，**届时将无法对协议层做单步调试**。`-Og` 是 GCC 专为调试设计的等级：保留完整调试信息、不做妨碍单步的优化。
   - 如需回到纯 `-O0`：把 `cmake/gcc-arm-none-eabi.cmake` 的 DEBUG 两行改回 `"-O0 -g3"`。

### 勘误（对我上一轮分析的三处更正）

1. **"`main.c` 缺 include 导致 2 个警告"** —— 我上一轮读的构建日志早于你的那次编辑，把"已修"报成了"未修"。以最终实测为准：`main.c:33` 已有 `#include "app_scheduler.h"`，**双配置 0 警告**。
2. **"`bsp_ssd1306_fonts.c` 19KB + `bsp_ssd1306_tests.c` 3.5KB 占全片 35%"** —— **错误**。我当时量的是残留的 `.obj`（`build/Debug` 当时被占用、删不掉），不是最终链接结果。真相：
   - `bsp_ssd1306_fonts.c` 源码 19KB，但 6 套字体里只有 `Font_7x10` 被 `#ifdef` 启用，**最终固件里只占 1,900 B**；
   - `bsp_ssd1306_tests.c` 已被 CMakeLists 的 `list(FILTER ... EXCLUDE REGEX "bsp_ssd1306_tests\\.c$")` 排除出构建，且即便编译也会被 `--gc-sections` 剔除（无调用者），**最终占 0 B**。
   - 教训：**判断 Flash 占用必须看链接后的 ELF 符号表（`arm-none-eabi-nm --size-sort`），不能看 `.obj` 体积。**
3. **"Flash 是阶段 2 的阻塞项"** —— 修正为**不是**。Release 整改前就是 68.15%，已满足余量要求；真正紧张的是 Debug（93.49%），其后果是**无法调试**而非**装不下**。整改后两者都有 ≥40% 余量。

### 对阶段 8（IAP）的结论随之修正

原先建议"Flash 不够就换 STM32F103CBT6（128KB）"。**不需要换芯片**：
- 64KB 确实装不下 A/B 双区（2 × 35.5KB = 71KB > 64KB）；
- 但**板上有 W25Q64（8MB SPI Flash）**，标准做法即可：**bootloader（约 4KB）+ 单一 app 区 + 以 W25Q64 作为新固件的中转暂存区**。新固件先写入 W25Q64 并校验，再由 bootloader 读出编程 app 区，失败可回退到 W25Q64 里的旧镜像。
- 这比换芯片改动更小，且顺带把 W25Q64 从"完全空转"变成关键部件（阶段 1 里它仍然没有任何调用者）。

建议在阶段 8 前把该方案定稿为正式 ADR。

### 1.1 🔴 A 类问题：构建不干净 —— `main.c` 缺少 include

`Core/Src/main.c` 的 include 列表止于 `retarget.h`（第 32 行），**没有 `#include "app_scheduler.h"`**。
于是 `App_Scheduler_Init()` / `App_Scheduler_Run()` 都是**隐式声明**：C 编译器按"返回 `int`、参数未知"处理。当前能链接成功纯属侥幸——返回值恰好没被使用，且两个函数签名恰好不需要参数传递约定上的巧合。一旦将来它们带上参数或返回值，就会出现极难定位的栈错乱。

**这正是阶段 1 自己定的验收标准"0 warning"所禁止的。**

**修法**：`main.c` 加一行 `#include "app_scheduler.h"`。

### 1.2 🔴 E 类问题：Flash 已用 92.79%，只剩 4.7KB

阶段 0 结束时是 **44,024 B（67.2%）**，阶段 1 后变成 **60,808 B（92.79%）**，增长 16.8KB。

**Flash 大户（实测 obj 体积）：**

| 文件 | 体积 | 说明 |
|---|---|---|
| `BSP/bsp_ssd1306_fonts.c` | **19,357 B** | SSD1306 库自带 6 套字体全开。OLED 只用来显示几行数字 |
| `BSP/bsp_ssd1306.c` | 4,215 B | 驱动本体 |
| `BSP/bsp_ssd1306_tests.c` | **3,562 B** | **死代码**——全工程无调用点，却被 CMake 的 `GLOB_RECURSE` 收进固件 |

也就是说 **22.9KB（占全片 35%）是 OLED 字体与测试代码**。

另外 `CMakeLists.txt:120` 仍保留 `-u _printf_float`，把浮点 printf 整套拉进来（数 KB 量级），而阶段 1 只用到 `%.1f` 这种简单格式。

**为什么这是验收项而不是优化项**：只剩 4.7KB 的情况下，
- **阶段 2** 的协议栈（CRC16 查表 512B + 收发缓冲 + 状态机 + 统计）**装不进去或极度勉强**；
- **阶段 8** 的 IAP 需要 bootloader + 双区，在 64KB 上**根本不可能**（这也是 `docs/05-决策记录-ADR.md` 待决策清单里"F103 是否换 128KB 型号"的触发条件，现在被提前触发了）。

**建议动作（按性价比排序）**：
1. 从 CMake 排除 `bsp_ssd1306_tests.c`（省 3.5KB，零风险）
2. 字体裁到 1~2 套（省 ~15KB）
3. 评估去掉 `-u _printf_float`，把 `%.1f` 改为整数定点打印（省数 KB）
4. 若仍不够 → 换 **STM32F103CBT6（128KB Flash，LQFP48 引脚兼容）**，这颗改动极小

> **📌 2026-10-18 复核实测（当前真实值）**：Debug 构建 **FLASH 46,044 B / 64 KB = 70.26%**，**RAM 8,584 B / 20 KB = 41.91%**。上文 §1 的 60,808 B / 92.79% 与 §0 整改表的 -O0→-Og 数字（39,492 B / 60.26% 等）均为历史快照，保留以备追溯；本文档其余处引用的旧体积一律以上述 2026-10-18 实测值为准。

## 3. 补充发现（未被验收项覆盖，但会影响阶段 2）→ ✅ 整改完成

> 下表为**整改结果**；原始描述保留在每条的"原始问题"里。

### 3.1 看门狗的双初始化与初始化空窗 → ✅

**原始问题**：CubeMX 的 `MX_IWDG_Init()`（PR=4/RLR=4095 ≈ **410ms 窗口**）在 `main.c` 就被调用，而把它改成 2s 的 `BSP_IWDG_Init(2000)` 要到 `App_Scheduler_Init()` 才执行；中间夹着 OLED（内含 `HAL_Delay(100)` + 约 30 次 I2C 命令写）、EEPROM、BMP280 初始化，且**全程不喂狗** —— 器件缺失或总线卡住时会被误复位。

**整改**：
- `main.c` **不再调用** `MX_IWDG_Init()`（保留注释说明原因），看门狗统一由 `BSP_IWDG_Init(2000)` 在所有外设就绪后启动 —— 410ms 窗口从此不存在
- 初始化各步之间**逐一 `BSP_IWDG_Feed()`**（掉电计数、PIR、OLED、BMP280、灌溉/门锁、蜂鸣器各一次）

### 3.2 `fault_cnt` 成功后不清零 → ✅（已在 §2.2 一并修复）

6 个文件（soil/rain/mq4/air/dht11/bmp280）的计数器全部提到函数作用域并在读取成功时清零。原先注释写着"读取成功 → 清零故障计数"但代码里没有这句，导致"连续 5 次失败才判故障"退化成"累计 5 次后任何单发失败即判故障"。

### 3.3 `app_scheduler` 不是调度器 → ✅ 补齐可观测性，有意保留串行模型

**原始问题**：无周期保证（`last_tick = HAL_GetTick()` 而非 `+= period`）、**无任何执行时间观测**、串行无抢占、崩溃点末尾被清成 `NONE` 导致"崩在循环体"这一信息丢失。

**整改**：
- **新增每任务耗时统计**：`RUN_TASK` 宏用新增的 `delay_micros()`（DWT CYCCNT）测量每个任务的耗时，记录"上次 / 历史最大"，并统计整个主循环耗时。主循环每 60s 打印 `[STAT]` 表，`[HB]` 心跳（改为 5s 一次）带 `max_loop=...us`。**这是阶段 2 设定协议 ACK 超时的直接依据** —— 有了它就不必照抄规范里的 50ms，而是按实测定（**最终定稿 `ACK_TIMEOUT = 100ms`，见 docs/12 决策 4 与 docs/03 §6.1；实测 3.6h / 13,064 帧 0 重传**）。
- **崩溃点标记改为 `SCHED_TRACE_IDLE`**：复位后读到 IDLE 即说明崩在循环体（心跳/统计打印）而不是某个任务里；原先把末尾置 `NONE` 恰好丢掉了这个信息。
- **`APP_LOCK_Task()` 不再无条件空转** → **2026-10-18 进一步清理**：锁确定不做（模块买错），`app_lock` / `bsp_lock` 已删除、调度器 LOCK 任务移除；PB8 由 `act_manager` 独占写、保持默认锁定电平。（整改当时是"加 `APP_LOCK_ENABLED` 编译开关、默认 0、由开关接入调度器"，此处为追溯更新。）

**有意保留（非缺陷）**：串行、无抢占、无 per-task 超时看门狗 —— 这是裸机前后台模型的固有属性，`docs/02-系统架构.md` 里已说明；是否需要 per-task 超时，等阶段 2 引入协议任务后按实测的 `[STAT]` 数据决定。**注意**：周期漂移（`+= period`）本次也未改，因为 `[STAT]` 会先给出实际循环耗时，届时能判断"漂移量是否值得修"——先测量再优化。

### 3.4 `app_data` 是裸全局 → ✅ 加时间戳、去冗余、写明并发约定

**原始问题**：无时间戳、无脏标记、无并发保护；六个 `g_xxx_data` 影子结构与 `g_sensor_data` 并行（两个事实来源）；`*_valid` 与 `*_quality` 语义重叠。

**整改**：
- **新增数据新鲜度时间戳**（`soil/gas/air/rain/dht11/bmp280/human/pump_tick`）与 `sensor_is_stale()` / `sensor_age_ms()`。这解决了"只看 valid 分不清坏数据与老数据"的问题 —— 串口输出已把状态列细分为 **INVALID / STALE / OK**。这也是阶段 3"影子状态 + 陈旧标记"的直接基础。
- **删除 6 个只写不读的影子结构**（soil/mq4/air/rain/dht11/human）。逐一核对过：它们的唯一消费者（OLED）早已改读 `g_sensor_data`，六者全是冗余 —— 百分比计算现在用局部变量，减少了 RAM 与"两个事实来源"的隐患。
- **写明并发约定**（`app_data.h` 头部）：`g_sensor_data` 是主循环单写者结构；唯一的硬件中断（PIR EXTI）不直接写它，只在 BSP 内更新自己的 static，由 `APP_HUMAN_Task` 读取后写入；因此当前不需要加锁。并明确写下："若将来新增在中断里直接写该结构的代码，必须同时引入临界区"。这条约定比"看起来没问题"可靠。
- **`valid` / `quality` 关系收口**：`valid` 现在只是 `quality` 派生出的布尔量（`sensor_valid_from_quality()`），头文件写明"新代码请直接用 quality，valid 保留是为兼容旧消费方"。


### 3.1 🟠 IWDG 的双初始化与初始化空窗

`Core/Src/iwdg.c:41-42` 配的是 `PR=4 / RLR=4095` → 超时约 **410ms**（LSI 取下限 30kHz 时仅 273ms），而它在 `main.c:102` 就启动；把它改成 2s 的 `BSP_IWDG_Init(2000)` 要到 `app_scheduler.c:91` 才执行。

当前夹在中间的只有 `MX_TIM4_Init` 与 `RetargetInit`（微秒级），所以没炸。但：
- **初始化段全程不喂狗**（第一次喂狗在 `app_scheduler.c:129`），而这段里有 `ssd1306_Init()`（内含 `HAL_Delay(100)` + 约 30 次 I2C 命令写）、EEPROM 写（各含 5ms 延时）、BMP280 校准读，**OLED 缺失或总线卡住时单次 I2C 超时可达 50ms，叠加起来逼近甚至超过 410ms** → 上电复位循环。
- 将来任何人在 `main.c` 的 USER CODE 区插入 >410ms 的初始化就会踩雷。

**建议**：删掉 `MX_IWDG_Init()` 调用（由 BSP 统一管理），或让它与 BSP 目标超时一致；并在初始化段的关键步骤之间插入喂狗。

### 3.2 🟠 六个模块的 `fault_cnt` 成功后不清零

`app_soil.c:33-40`、`app_rain.c:33-39`、`app_mq4.c:44-48`、`app_air.c:41-45`、`app_dht11.c:45-48`、`app_bmp280.c:45-48` 的写法一致，且 **`app_soil.c:39` 的注释 "读取成功 → 清零故障计数" 所在位置正是应该清零的地方，但代码里没有清零语句**。

后果：计数器只增不减 → **累计第 5 次之后，任何一次单发失败就直接置 FAULT**，与设计意图"连续 N 次失败才判故障"不符。

### 3.3 🟠 `app_scheduler` 不是调度器，是"顺序编排 + 崩溃追踪 + 看门狗"

这一点需要统一认识，因为它影响阶段 2 的任务设计：
- 无时间轮、无任务表、无优先级、**无周期保证**（各任务仍用 `last_tick = HAL_GetTick()` 自节流，而不是 `last_tick += period`，所以循环耗时被累加进周期 → 长期单调漂移）
- **无 per-task 超时、无执行时间统计**
- 串行无抢占 → **一个任务慢会拖慢所有任务**。最坏路径叠加可达数百毫秒：DHT11 ~24ms + OLED 整帧 25~90ms + BMP280 I2C 超时 100ms + OLED 每页 50ms×8 = 400ms 级
- `g_sched_trace` 在第 169 行被复位为 `NONE`，所以卡在调度器自身或心跳时会丢失定位信息（复位后只能打印 NONE）

**这对阶段 2 的意义**：协议需要**确定性的收发时序**（原规范写 ACK 50ms 超时，**最终定稿 100ms**；重传、帧内字节超时 20ms）。当前"最坏 400ms 的串行主循环"会让协议超时机制**完全失效**（ACK 还没发出去，对端已经判定超时重传了）。
**阶段 2 开始前必须做的架构决策**：把"协议收发"从主循环里独立出来（要么给 USART1 配 DMA + IDLE 中断 + 独立任务，要么至少让 ACK 走中断/硬件路径），不能排在 OLED 刷屏后面。

### 3.4 🟠 `app_data` 仍是裸全局，无时间戳/无脏标记/无并发保护

- `g_sensor_data` 是 `extern` 裸全局（`app_data.h:99`），无锁、无临界区、非 volatile
- **无时间戳**（没有 `*_tick`）→ 阶段 3 的"影子状态 + 陈旧标记"没有依据
- **无版本号/序号**→ 阶段 2 的"状态变化上报"没有依据
- `*_valid` 与 `*_quality` **两套有效性并存**，且各消费者各取一半（控制用 valid、显示用 quality）→ 这正是 T-03 想统一却没收口的地方
- 六个 `g_xxx_data` 影子结构（`g_soil_data`/`g_air_data`/…）与 `g_sensor_data` 并行存在，仅 `percent` 被 OLED 使用，属冗余

## 4. 验收结论

**不通过（有条件）。**

阶段 1 的工作量和完成度是实实在在的：ADC 合并、引脚集中、W25Q64 三项加固、OLED 有限超时、PIR EXTI、蜂鸣器 TIM、IWDG、EEPROM 掉电计数、灌溉合并、DMA retarget 这些**都是正确且质量不错的重构**。

但下列 5 类问题使它无法直接进入阶段 2：

| 类别 | 问题 | 为什么是阶段 2 的前置条件 |
|---|---|---|
| **A 构建** | `main.c` 缺 include → 2 warning | 阶段 2 要加大量新文件，构建不干净会掩盖真问题 |
| **B 数据** | MQ ppm 恒 100、预热期参与告警、土壤断开误灌溉 | 数据不可信时，阶段 2 用它做协议联调只会得到错误结论 |
| **C 时序** | DHT11 关中断 24ms → tick 慢 1%；主循环最坏 400ms 串行 | **协议的 ACK 超时/重传/帧内超时全部依赖准确 tick 与低延迟主循环**，不修则协议无法调试 |
| **D 保护** | 干烧保护无限重启、fault_cnt 不清零 | 安全逻辑失效会在长跑测试中造成误导性故障 |
